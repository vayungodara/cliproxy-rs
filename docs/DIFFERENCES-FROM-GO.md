# Differences from Go CLIProxyAPI

The compatibility target is frozen at CLIProxyAPI v8.0.35, commit `ae3ee3be303fb07fb8173279923413005bf32177` ([PARITY.md](PARITY.md)). This page records deliberate differences and implementation limits; it does not claim that every newer Go feature is ported. Existing fixtures retain their original Go versions. Missing or unproven v8.0.35 contracts are tracked in the [parity audit](parity-audit/status.md), with the intervening commits in the [upstream inventory](parity-audit/upstream-v8.0.35.md).

## Additions in cliproxy-rs

- Routing strategy `soonest-reset` (alias `reset-first`), experimental and opt-in: select the account whose weekly window resets soonest, until it cools down or reaches a limit, then move to the next. An account whose reset time is not known yet gets one probe request. Conversations bound to an account stay on it. Go has only `round-robin`, `weighted-round-robin` and `fill-first`, and reads `soonest-reset` as `round-robin`. The dashboard offers it only when it is connected to cliproxy-rs. See [MULTI-ACCOUNT.md](MULTI-ACCOUNT.md#routing-strategies).
- Codex connection reuse, opt-in: `oauth.providers.codex.chatgpt-keep-alive: true` makes the Codex client for `chatgpt.com` (the Chrome TLS fingerprint) keep up to 2 idle connections per host and proxy for 90 seconds and send later requests on them, several at once over HTTP/2. The ClientHello, the request headers and the proxy are the same, and connections never cross proxies. Off, the default, it does what Go does: a dedicated connection per request, closed with the response body (`helps/utls_client.go`). The setting applies from the next request after a config reload. Go starts with the key in the file and ignores it. A config edit through Go's v8 Management API moves the key into a comment, so the setting is off again when you return to cliproxy-rs; edits through Go's v0 endpoints keep it. Setting the key through Go's v8 API is refused, as for any key Go does not know.

- Usage record additions: each record in the usage queue (`GET /v0/management/usage-queue`, `GET /v8/management/observability/usage/queue` and the RESP `usage` channel) gains, after Go's fields, `session_source`, `prompt_prefix_hash`, a `timings` object and three byte counts, to show which conversation a request belongs to and where the time to the first token goes. Go's `session_id` is already the conversation: the session key the server derives for every request, whether or not `routing.session-affinity` is on, as a UUID (a client's UUID as sent, anything else hashed). `session_source` says where that key came from: `header` (a client session header such as `X-Claude-Code-Session-Id`), `metadata` (a session in Claude's `metadata.user_id`), `user_id` (a plain `metadata.user_id`, which names a user rather than one conversation), `body` (another body field such as `prompt_cache_key` or `conversation_id`), `execution` (a Responses WebSocket session), `derived` (no session signal: a hash of the leading instructions and the first user input, so it changes with the system prompt), `messages` (the first-messages hash), `lcp` or `home` (the session that session affinity or Home bound the attempt to). `prompt_prefix_hash` is 16 hex digits, the first 64 bits of a SHA-256 over the client's `tools` and system prompt (`system` for Messages, `instructions` for Responses, `systemInstruction` for Gemini; none for other formats) as the route passed them on, before plugin interceptors, translation and cloaking, `cache_control` markers included (the Messages route passes them on as sent; the Responses routes may first have rewritten a Codex client's multi-agent tools), so another mode or a subagent shows as another value; no prompt text is recorded. Claude attempts also add `claude_cache`: final upstream TTLs, hashes and byte sizes of the serialized fingerprint input, hashed session and account scope, request kinds, and absolute attempt timestamps. Returned five-minute and one-hour cache-write buckets appear in `tokens` only when Anthropic supplies them. See [Claude cache telemetry](CLAUDE-CACHE-TELEMETRY.md) for the schema and offline replay limits. `timings` holds milliseconds since the server accepted the client request: `client_body_received_ms` (the request body was read to its end), `upstream_started_ms` (the upstream request is about to be sent), `upstream_connected_ms` (the HTTP client has a connection and starts writing the request), `upstream_connection_reused` (`true` when the request went out on a pooled connection; left out when a connection was dialled while it waited, since the client may still have used a pooled one that came free first and does not say which), `upstream_body_sent_ms` (the client took the last of the body into its write buffer: handed over, not acknowledged by the upstream: the client takes another 64 KiB piece while its buffer holds less than 408 KiB, so under 472 KiB of the body plus what the kernel's socket buffer holds may still be on its way), `upstream_headers_ms` (the response head arrived), `upstream_first_byte_ms` (the first response body bytes arrived) and `client_first_byte_ms` (the request's first response bytes were handed to the client's connection before the record was published: a stream's first event, or a keep-alive sent while a buffered response waited; a buffered response without one publishes its record before its body is written and leaves it out). `client_request_bytes`, `upstream_request_bytes` and `upstream_response_bytes` (as received, before content decoding) follow. A field that was not seen is left out. The Claude executor fills them all, for Claude credentials and for the Kimi requests it serves (Anthropic Messages); other executors leave out the upstream fields. `upstream_connected_ms` and `upstream_body_sent_ms` are reported only where the upstream speaks HTTP/1.1: `api.anthropic.com` and plain `http://` base URLs. A Responses WebSocket turn counts from the start of the turn and has neither the client body fields nor `client_first_byte_ms`. A record covers one upstream attempt, so a retried request's later attempts show when they started. When the upstream redirects, the upload fields describe the last request sent: a redirect followed as a GET has `upstream_request_bytes` 0 and no upload times, and a hop that is not timed leaves them out. While usage statistics are on, a request body goes to such an HTTP/1.1 upstream in 64 KiB pieces instead of one, with the same bytes and `Content-Length`. Go's record has none of these fields; readers that ignore unknown fields are unaffected, and usage plugins get Go's record unchanged.
- `worker-threads` (top level of `config.yaml`): the number of request threads, by default the smaller of the CPU count and two; see [CONFIGURATION.md](CONFIGURATION.md#worker-threads). Go sizes its scheduler by the CPU count. The key is read once at start from the `-config` file (`./config.yaml` by default), before a remote store or Home supplies a config; in a store's `config.yaml` or in the config Home supplies (the local `-config` file still applies) it has no effect, and those deployments set `TOKIO_WORKER_THREADS` instead. Go starts with the key present and keeps it through v0 Management API saves. Any v8 configuration write (PUT, PATCH or DELETE under `/v8/management/config`) turns it into a `# worker-threads: N` comment and logs `unrecognized configuration section "worker-threads" commented out during v8 migration`, and `PUT /v8/management/config.yaml` with the key answers `unknown v8 configuration section worker-threads`. When one config.yaml is shared with a Go server, set `TOKIO_WORKER_THREADS` instead.

Claude cache observations require the separate default-off
`observability.usage.claude-cache-telemetry` opt-in as well as usage statistics.
The `bytes` values measure serialized fingerprint input, including path and role
strings and tuple JSON framing, not raw section lengths or token counts. Claude
cache telemetry hashes use a private random process-local HMAC key and rotate
on restart, including identities derived from configured API keys.

The queue and RESP channel gain additional zero-token observations marked
`usage_observed: false` on `Ending::Done` (completion or client drop) only when
all these conditions hold:

- The attempt was not discarded and has not already been published.
- The executor has not published an outcome.
- The executor marked the attempt as usage-required, but no usage was observed.
- Collected Claude telemetry is present, requiring the telemetry opt-in and usage
  collection to be enabled.
- The usage queue accepts records (management and usage statistics are enabled).

Go emits no record on this no-usage path. The additional records' zeros mean
unknown usage, and `failed: false` does not establish success. Failed attempts do
not receive this marker, and the additional observations do not reach Go plugins.
A native non-streaming Claude JSON response without usage still publishes an
ordinary record through its executor-supplied outcome, without this marker.
Absence of the marker therefore does not prove that usage was observed.
Ordinary records and usage plugins keep Go's accounting.

## Deliberate differences

- Claude Code identity: a native Claude Code `User-Agent` at or above the measured baseline (2.1.280) within the same major version is forwarded to Claude accounts. Go forwards only patch releases of the baseline's 2.1 line, so Claude Code 2.2 and later would be sent as 2.1.280 and treated like a third-party client. A forwarded release newer than the baseline must send well-formed `X-Stainless-Package-Version` and `X-Stainless-Runtime-Version` headers, which go upstream with it; without them it is cloaked as 2.1.280, as before. Go replaces both headers with the baseline values, so its headers can disagree with the forwarded `User-Agent`. The Haiku helper requests of such a release (session titles, quota probes) follow the same rule while their measured beta and body shapes hold; Go confirms a helper only with the exact baseline tuple. When cliproxy-rs adds a billing block to a forwarded newer release, the block's `cc_version` is that release's version; Go uses the baseline's. With `stabilize-device-profile` on, Go's 2.1 patch rule applies unchanged, because a stabilized profile forwards only the exact baseline tuple; the Stainless requirement, the helper rule and the billing version above apply only without stabilization. A `claude-cli` `User-Agent` that is refused while the baseline identity is sent is logged at most once per credential and version (64 slots per credential, so two versions can share one line), naming the credential by its auth index.
- Thinking off on Claude models that refuse it: a model with registry capabilities (catalog, configured or plugin) turns thinking off exactly as Go v8.0.35 does: with its `disable-type` (`between_tools` on Sonnet 5.5), else `disabled`, or at its lowest effort when its capabilities do not allow zero (Opus 5.5, Fable 5 and 5.1). Only without registry capabilities, where Go always sends `disabled` (`applyCompatibleClaude`), cliproxy-rs keeps a fixed list of models that answer 400 to `disabled` (Opus 5.5, Sonnet 5.5, Fable 5 and 5.1 and Mythos, per Anthropic's thinking troubleshooting table): `reasoning_effort: "none"`, a zero thinking budget or `thinking: {"type": "disabled"}` sent to one of them as a user-defined model (including an alias whose body names one) or as a model the registry lacks, such as Mythos, becomes adaptive thinking at effort `low`.
- Claude caller system prompt with an API key and cloaking: on a current model, outside strict mode and without advisor results in the conversation, the caller's system prompt is sent as a system turn after the leading user turns, in Messages and count_tokens alike and on every turn of a conversation, as for an OAuth login. Go v8.0.27 keeps it in the top-level `system` for an API key while the leading user turns end the conversation or there are several of them (`5d89040`, `eca1d11`, `39632e5`). v8.0.35 still does: it passes `!policy.OAuth` into the top-level placement policy (`claude_executor_cloaking.go`, `claude_executor_tokens.go`). Its first request of a conversation then sends the prompt top-level and the second moves it, so the second request differs from the first right after the Claude Code identity block and the prompt cache is written again from there. `6fecc6e` placed the prompt after the first user turns on every turn, as cliproxy-rs does. Payload rules run after that placement and nothing repairs their result (868e137), so when a rule then picks a model that predates mid-conversation system turns, cliproxy-rs refuses a Messages request to first-party Anthropic with Go's 400 `invalid_request_error: role 'system' is not supported on this model`, where Go sends an API key's first turn with the prompt still top-level. count_tokens checks before the rules and third-party origins skip the check, so neither refuses.
- Payload rule parameter order: one `default`, `default-raw` or `override` rule that adds several new keys adds them in the order the config lists them. Go keeps a rule's `params` in a Go map, whose iteration order is random, so the same request can reach the upstream with those keys in a different order from one request to the next. The values and the set of keys are the same. Likewise, an images multipart form that the rules changed is rebuilt with its parts in the order of the rules' JSON result; Go writes them in random order.
- Payload rule paths: cliproxy-rs applies only paths its JSON port reads exactly as Go's gjson does. Those are dot- or pipe-separated plain keys and indexes, with `\` escapes and `*`/`?` wildcards; a bare `#` (a count, or `#.key`); `@this` without arguments; and whole `#(query)` or `#(query)#` parts whose predicate has no `@`, no `|` and no nested query, and in which each `&&`/`||` term is one query whose path is itself in this set. A parameter with any other path is dropped after Go's whole-rule check of raw values, so an invalid raw value still drops its whole rule. A model entry whose `match`, `not-match`, `exist` or `not-exist` path is outside that set never matches. Examples are subselectors (`[a]`, `{a}`), modifiers other than `@this`, `@this` with arguments, static values (`!true`), JSON lines (`..`), `#[...]`, queries after a pipe or with `@` or `|` in the predicate, and quotes or parentheses in a plain key. Go reads these with gjson, and its edits go through sjson, which parses the same path differently. Its results vary: `[a].#(k==1)#.x` changes nothing, an `@reverse` override changes nothing but marks the path as applied, an `exist: ["{a}"]` condition holds for any object body, and `not-exist: ["a(|@reverse"]` holds when the key `a(` is missing.
- Token counts and the payload rule baseline: on the Claude, Gemini, Vertex, Codex and OpenAI-compatible `count_tokens` paths, a client's original request that fails to translate (for example a Claude user turn whose only block is a `container_upload` file source, which Gemini cannot inline) refuses the count with that translation error, whether or not any payload rule is configured. Go keeps the partial body its translator returns alongside the error and checks `default` and `default-raw` rules against it, so the count proceeds and a default the client already set is not added. cliproxy-rs has no partial body to check against, and an empty baseline would add the default.
- Codex and xAI WebSockets: writing one frame upstream is bounded to 10 seconds, or to the frame's size at 128 KiB per second (rounded up) when that is longer. A write past the bound fails like any other write: if the upstream already closed the socket with 1009 (message too big), the request gets the same 413 as a failed write; otherwise the socket is dropped and the request is retried once on a new socket, or answered with a replay request on a continuation. On a steering (duplex) stream, a failed or timed-out write after the stream started ends the stream with that error. A client's `response.interrupt` written to the socket of the turn in progress has the same bound; when that write fails the socket is dropped, and the client gets the write error as a 400 error event (Go returns the error and leaves the socket to its reader). Go sets no write deadline, so a half-open socket held the request until the 300-second read deadline.
- Upstream connections: the Claude client for `api.anthropic.com` keeps every idle connection for 90 seconds. Go's transport for it keeps at most 2 idle connections per host (net/http's default) with no time limit, so after a burst of concurrent requests Go dials again and cliproxy-rs does not.
- Upstream timeouts: a request with a fixed timeout (Kimi and xAI sign-in and token refresh, the Management API `api-call`) gives all its redirect hops one deadline, as Go's `http.Client.Timeout` does. Reading the final response body is bounded separately, by the time that was left when its request was sent, so a slow body can stretch the exchange to at most twice the timeout. Go's deadline also covers the body.
- Quota cooldowns (`routing.cooldown.max-trusted-cooldown`, a bug fix, on by default): when an upstream answers 429 with a reset time (Codex `usage_limit_reached` with `resets_at`, Claude's `anthropic-ratelimit-unified-*-reset`, or `Retry-After` from any provider), Go rests the account until that time, even when it is days away, and never asks again. Providers often reset early, which leaves the account unused until the stated time or a restart, and with `save-cooldown-status` a restart restores the same wait. cliproxy-rs rests the account for at most one hour at first, then lets the next ordinary request through as a check (no timer or background request). Only that one request goes upstream: until it is answered (or for at most 30 seconds), other requests see the account as cooling, and retries never wait for such a window. Only the probe's own answer or cancellation ends the check: an answer or cancellation from a request picked before it, including an earlier probe whose 30 seconds ran out, neither frees the account nor opens the next window. A streamed answer counts as soon as its first event arrives, so other requests use the account while the stream runs. One exception: when one model of a pooled `openai-compatibility` model alias (several models under one alias name) has its own window (not the account's), requests for the alias that arrive together after that window ends can each probe that model, because the reservation is taken for the alias at pick time and the pool chooses its model later. Each window that ends in another 429 doubles the next, a success ends the escalation, and the rest never passes the stated reset except by Go's own additions: its 10-second minimum and the 1 to 30 seconds of random delay it adds to Claude's reset. A success from a request picked before the window opened (a stream that outlived the 429) leaves the window to its probe, even after the window ended; Go keeps a cooldown against such a success only while the cooldown runs, and clears it on any success dispatched after the 429. A concurrent 429 inside a window keeps the window, or shortens it when it states an earlier reset. The account's probe answers the account's window, not a model's own window: that model keeps its own probe time and gets its own probe. Under the account's bounded window, a model's own cooldown of any cause keeps its own deadline in that model's record, and the account's record holds the model until the account's probe, so an earlier account reset never brings the model back sooner; Go writes the later of the two deadlines into the model's record. The doubling count is separate from Go's `backoff_level` (which keeps its meaning) and is saved as an extra `quota.trust_windows` field on every quota record cliproxy-rs writes to `.cds` files, which Go ignores; records are saved only while their cooldown is running, so a restart after a window ended starts again at one hour. cliproxy-rs's own records restore as they were saved. `.cds` records written by Go or before this change get the first bound. A model's count is never lowered by a credential-wide window. The stated reset is kept: `.cds` records and error events report it as `quota.next_recover_at` (Go's meaning) and the probe time as `next_retry_after`, and the Management API's cooldown entries gain `recover_at`, so the dashboard shows "Limited until X · next check in Y"; such an entry stays listed, with `remaining_seconds` 0, after the window ends while the stated reset is ahead. The cost is one comparison per 429; a probe check on two keys per recorded result, per pick and per stream start; one scan of the cooldown entries when a stream start or a success ends an account's window; four bytes per cooldown entry and per request for the window generation; and per credential and model one real upstream request per window. `max-trusted-cooldown: 0` restores Go's behaviour. Set by a config reload, it applies to requests picked after the reload. A bounded window keeps its bound and ends with its probe, unless a 429 from such a request arrives inside it with a later stated reset, which then replaces the bound as in Go. Go starts with the key in `config.yaml` and ignores it; when Go's Management API rewrites the file, it moves the key into a comment, as it does with every key it does not know.
- Claude Responses compaction: a forged compaction capsule (one that decrypts but is not capsule JSON) fails with cliproxy-rs's own error text, not Go's `json.Unmarshal` message, as for Antigravity.
- Claude per-minute 429s with a repeated JSON key: when an Anthropic error body repeats a key byte for byte, only the last value counts, so `{"error":{"type":"rate_limit_error","message":"This request would exceed the requests per minute rate limit. Please try again later."},"error":null}` is not read as a per-minute error and the credential cools until the unified reset instead of for the short `Retry-After`. Go's `encoding/json` ignores the later `null` and narrows the cooldown. Anthropic does not repeat keys; differently cased keys (`Error`, `ERROR`) and differently named ones are read as Go reads them.
- Startup: if the config fails to load outside cloud deploy mode, cliproxy-rs exits with a non-zero status, so a service manager sees the failure. Go exits 0.
- Discovery: subtype PTR queries are answered (Go's zeroconf library never matches them) and answers go out on every selected interface.
- `.env`: non-UTF-8 bytes inside quoted values are decoded lossily. Go keeps the raw bytes.
- OAuth sign-in from the Management API: pending callbacks are held in memory with the sign-in session instead of being written to `auth-dir` as `.oauth-<provider>-<state>.oauth` files.
- Claude: `platform_url` is HTML-escaped on the sign-in result page, credential files are written atomically with mode 0600, and the SSH port-forwarding hint shows the IP address of the outbound interface.
- Plugins: loading plugins on Windows is not supported, the same as a Go build without cgo.
- Plugins, native shadow copies: Go loads each native library from a content-addressed copy in the shared `$TMPDIR/cliproxy-pluginhost/pid-<pid>` and trusts whatever it finds there, so another local user who can create that directory first can swap a library between its hash check and `dlopen`. cliproxy-rs keeps the copies in `$TMPDIR/cliproxy-pluginhost-<euid>/pid-<pid>`. It checks the per-user directory before the process directory, and each must be a real directory (not a symlink) owned by the effective user and not group- or other-writable; new ones are created `0700`. Anything else fails the load with an error naming the directory, and nothing is repaired. An existing copy is reused only when it is a regular file owned by that user, writable by nobody else, with the expected size and SHA-256; a symlink or any other file is replaced. Stale directories of exited processes are deleted only after the same check. This still trusts `$TMPDIR` itself, a sticky `/tmp` or a private directory. The copies are mapped executable, so on a `noexec` `/tmp` set `TMPDIR` to a trusted directory that allows it: a failed load names the copy's path, and there is no automatic fallback. Because the directories differ, cliproxy-rs and Go no longer remove each other's stale copies.
- Request body limits: the client routes refuse a body over 64 MiB, which Go reads whole when `server.max-request-body-bytes` is not set; a configured limit above 64 MiB acts as 64 MiB there. Such a body gets `400` with axum's plain-text reason, and a zstd body that decodes past 64 MiB gets `400` when the configured limit is higher. Under a configured limit, the handlers Go v8.0.35 changed (dd7b4334) answer Go's `413` bodies. A few Management handlers that Go left at `400` read their body whole before they run, so a body stopped at the limit gets the same `400` status as in Go but axum's plain-text reason instead of their JSON body: `PUT /v0/management/config.yaml`, `PUT` on the v0 key lists, and the v0 setting routes such as `PUT /v0/management/debug` when the bytes before the limit do not hold a complete JSON value (a complete first value binds, as in Go).
- Plugins, size limits where Go reads without one: a plugin frontend auth provider reads a request body of at most 64 MiB, the same limit as the routes, and a larger one is refused with `413` and `{"error":"request body too large"}` even when no key was sent. Plugin store responses (the registry, release metadata, release assets and direct artifacts) stop at 256 MiB, and a declared artifact size can only lower that. A library inside a plugin archive may expand to at most 256 MiB. `host.http.do` buffers at most 64 MiB of a response and then fails as a read error; `host.http.do_stream` is not limited. A quota probe's answer is read up to 64 MiB, like `requests/api-call`.
- Plugin store: a GitHub `X-Ratelimit-Reset` later than the end of year 9999 is treated as that time, so the cooldown stays printable. Go keeps any value.
- Discover mode: before plugins load, a flag that cliproxy-rs does not define (it may be a boolean flag a plugin adds) does not take a following `-discover` or `-discover-json` as its value, so `-some-plugin-flag -discover` runs discovery without loading plugins or `.env`. Go treats every flag it does not know as taking a value, then loads plugins and `.env` before the full parse selects discovery. Flags cliproxy-rs defines behave as in Go.
- Plugins, `.env`: the file is read before the plugins that add command-line flags load, so they see its variables. Go reads it after the flag parse.
- Plugin sign-in: when a sign-in returns several auth files and a later one fails to save, the earlier ones are undone without losing data. A file the sign-in created is removed, locally and from the configured store; a file that existed before gets its earlier contents back, and the store copy is synced from it. Go deletes both kinds, together with their store copies.
- Home mode, config updates: config payloads that arrive while an earlier one is being staged or applied are coalesced, and only the newest is applied, with its plugin sync, delete tasks and plugin status report. Go applies every payload in turn and skips to the newest only after a stage failed, so it can sync and report plugins for an intermediate config.
- Home mode, plugin sync key: a new config payload starts a plugin sync when a plugin's settings change, including a value written another way (`1.50` to `1.5`), as in Go, which hashes each plugin's raw YAML node. An edit to only a plugin's comments or quoting style (`'a'` to `"a"`) starts one in Go and not in cliproxy-rs; the plugins get the same values either way.
- Home mode, config API keys: the provider API keys in Home's config register their models, as in Go, and a key removed from a later config is dropped with its models. Go only adds and updates them, so a removed key's models stay listed until restart.
- Plugins, frontend auth: the metadata a plugin returns with an accepted request is not kept. In Go only Home mode reads it.
- Plugins, startup: plugin catalogs and executors are registered before the server accepts requests. Go registers them just after its listener starts (without Home), so its first requests can arrive before plugin executors exist. When a plugin sync changes the published catalog, cliproxy-rs decides executor ownership again against the new catalog (at most three passes), so a removed built-in catalog hands its models to a plugin executor in the same sync; Go decides once against the previous catalog and catches up on the next sync. A built-in provider reserves catalog models only while an enabled credential uses it (or always, for Go's baseline providers in Home mode); Go keeps a built-in executor bound after that provider's last credential is removed.
- Plugins, model routers: the available providers sent to a router list Kimi credentials typed `kimi.com` or `kimi.ai` under those keys, because credential selection here matches the key as written. Go lists them as `kimi` and `kimi-ai` and folds both spellings when it selects.
- Plugins, schedulers: a plugin scheduler that delegates to `round-robin` or `fill-first` continues the configured selector's rotation instead of a separate built-in rotation, and each candidate's `Status` is `active`, since only ready credentials are offered and an earlier failure is tracked as a cooldown rather than an `error` status. A credential the scheduler picks is checked again when its answer arrives: one that stopped being ready during the call (disabled, removed or cooling down) leaves the choice to the configured selector, where Go serves it from the snapshot it offered.
- Plugins, `host.http.*`: a URL whose host Go's parser and the WHATWG parser read differently is refused instead of being sent.
- Plugins, response translator hooks on streams: a stream decides when it starts whether the plugin response hooks run. A translator plugin loaded mid-stream applies from the next stream, while one unloaded or fused mid-stream stops at its next chunk. Go reads the hooks again for every chunk.
- Plugins, auth files a plugin auth provider parses: plugins parse an auth file before the reload that publishes it takes the lock management writes hold, so a file that changes in between (or a new auth folder the config switches to) is published at the watcher's next reload, usually within a tenth of a second. Until then a changed file keeps its current credentials and a new one has none. Go's watcher asks the plugins while it reloads. The exception is a plugin saving the file it is parsing (`host.auth.save` from inside `auth.parse`): when the file holds exactly the bytes that save wrote, a handled parse's answer is published at once and the saved bytes are parsed on the next reload, as Go parses them on the write's event (an unhandled answer waits for that parse); a save by another plugin or request to that file during the parse is treated the same way, until the watcher's next re-parse. Uploads register their built-in credential at once, as in Go.
- Plugins, `host.auth.save` to the file a plugin is parsing: Go parses saved data through the plugin auth provider before writing it. A save that a plugin makes from inside its own `auth.parse` of that file, on the thread the parse runs on (a native plugin's synchronous callbacks arrive there), writes the file without parsing it again; the parse's answer is published and the saved bytes are parsed at the watcher's next reload. Go recurses through the plugin without bound and never writes the file. A save of that file from another thread while the same plugin is parsing it for an earlier save is refused and writes nothing; Go parses it, which succeeds or recurses (a parse that saves from a goroutine it spawns recurses one thread per level). Every other save is parsed first, as in Go.
- Plugins, file names a plugin auth provider returns: a credential a plugin parses is listed (`host.auth.list`, the auth-files view) under its file's name, and a `host.auth.save` whose parsed auth names another file (`FileName`) is refused before the write. Go keeps and lists the plugin's file name.
- Plugins, credential files a plugin parses: each parsed credential keeps one JSON document, the plugin's storage JSON overlaid with its metadata (the document Go saves for it), and plugin calls receive that document as both `AuthMetadata` and `StorageJSON`. Go passes the plugin's metadata alone as `AuthMetadata`. Fields only the storage JSON holds, such as `weight` and `headers`, therefore take part in the parsed credential's weight validation and header attributes. The label and disabled state come from the plugin until a metadata change recomputes them from the document, as for every credential.
- Plugins, models of credentials with another provider: a credential whose provider has no built-in models (none of `gemini`, `gemini-interactions`, `vertex`, `aistudio`, `antigravity`, `claude`, `codex`, `kimi`, `kimi-ai`, `kimi.ai`, `kimi.com`, `xai`, `devin`, `meta`), with no `compat_name` and not of the `openai-compatibility` provider, such as a plugin or Home-dispatched auth of provider `zed`, registers its provider's plugin models under its lowercased provider. A `provider_key` attribute doesn't change that. Go registers them as an OpenAI-compatible credential: the models of the `openai-compatibility` entry named like the provider (case-folded), if any, followed by the plugin models of its key, under its lowercased `provider_key` (`Foo` registers under `foo`), or under the provider without one. So a provider `Acme` credential lists an `Acme` entry's models in Go and none here.
- Plugins, credential refresh: a plugin auth provider refreshes only credentials of providers outside the built-in executors (plugin executor credentials and OpenAI-compatible ones, as in Go). A credential typed as a built-in provider (`claude`, `codex` and the others) keeps its built-in refresh even when it carries a `compat_name` attribute, where Go binds it to the OpenAI-compatible executor and refreshes it through a plugin auth provider matching that name. A plugin refresh response that moves the credential to another provider is refused, and the credential stays as it was; Go saves the refreshed file with the new provider's `type`, so the file belongs to that provider from its next load. (A response with another ID fails in both: Go cannot commit it.) The response's prefix and attribute changes are not applied until the file is next loaded, which gives both the parsed values; Go merges them into the running credential at once without saving them. The refreshed tokens and document are saved, and a warning names the fields. The document is Go's: the refreshed storage overlaid with the metadata, with the response's `disabled` state and the merged `proxy_url`, which the running credential takes at once, as in Go. A failed plugin refresh always holds the next one off for 5 minutes, or until the access token expires when that is sooner; Go uses a growing backoff for an invalid grant and retries at once after a 401 on an expired token. A refreshed result that cannot be saved takes the same backoff; Go sets none for it. Refreshed storage that does not decode as a JSON object fails the refresh and leaves the credential as it was; Go logs the failed save and still uses the refreshed credential until the next reload.
- Plugins, refresh state after a disabling save: a `host.auth.save` that disables a credential drops its inherited refresh state (`LastRefreshedAt` and `NextRefreshAfter`) at once; it keeps its own parsed `NextRefreshAfter`. Go drops them when its watcher next reads the file, so an enabling save that lands before that read keeps Go's earlier last refresh.
- Plugins, refresh deadline after a management status change: Go's watcher parses an auth file again after management writes it, so a plugin credential that management disables or enables takes the `NextRefreshAfter` its plugin returns for the new bytes. Management here registers the change without asking the plugin. `PATCH /auth-files/status` on an auth file re-synthesizes the file's credential with the built-in synthesizer, so it registers without a `NextRefreshAfter` and is due by its interval. On a credential parsed with others from one source file, the status change keeps the `NextRefreshAfter` that credential's last parse returned. The watcher's next reload registers the parsed credential again only if it differs from the one management registered.
- Plugins, credential refresh in Home mode: with Home enabled, credentials that only a plugin auth provider refreshes (OpenAI-compatible ones through `pluginRefreshCompatExecutor`) are not refreshed automatically, and a management refresh of one takes its executor's own refresh. Go asks Home to refresh them first (`RefreshAuthViaHome`), then the plugin.
- Logs: structured fields that Go does not define are printed after Go's known fields.
- Case-insensitive matches against fixed ASCII words: where Go compares a free-form value with an ASCII literal through `strings.EqualFold` (for example a provider, protocol or thinking type), Go also accepts U+212A KELVIN SIGN for `k` and U+017F LATIN SMALL LETTER LONG S for `s`, and cliproxy-rs compares those sites in ASCII only. Comparisons between two free-form values follow Go's `EqualFold`.
- Process logs: the opt-in `--log-file PATH` flag replaces stdout through the existing 10 MiB rotating logger. With a positive `logs-max-total-size-mb`, its rotations share that budget with the normal log directory, even when PATH is elsewhere; the existing cleaner removes oldest logs on its minute schedule. With the default `0`, normal logs remain unlimited, but PATH's timestamped rotations have a separate 32 MiB total cap, enforced at startup, reconfiguration and rotation without another timer. Neither cleanup path deletes the file open for writing; that active file can exceed the budget. Outside the normal log directory, only PATH and its timestamped rotations are counted. `logging-to-file: true` still selects `main.log`, the dashboard log view and the existing size cleaner; turning it off returns to `--log-file`. Only the plain Windows server detaches its console, just before serving; login, import, discovery, TUI and plugin commands keep it. One output file is open when enabled, with no added thread, timer or work on inference requests beyond existing log writes. Go has no such flag.
- Working directory: the opt-in `--working-dir DIR` flag changes directory before `.env`, plugin bootstrap, config or relative paths are read. Windows installer launches pass it at sign-in as well as after installation. It has startup-only cost and is not passed in Go's plugin command-line values. Go has no such flag.
- Release checks: the dashboard checks only when clicked. `GET /server/latest-version` fixes the previously empty release URL using one anonymous HEAD to the public cliproxy-rs latest-release redirect, without following it. A successful tag is cached for 12 h (one timestamp and tag, no expiry timer). `CLIPROXY_NO_UPDATE_CHECK=1` disables checks at startup. Release checks use the configured `proxy-url`, or the environment proxy when none is set, and never send tokens or cookies; proxy credentials go only to your proxy, with TLS verification on and redirects off. Go asks its GitHub API on every call and can attach `server.github-token` or environment tokens; omitting those tokens is a credential-leak fix. Inference requests incur no added work.
- Config writes: when the Management API changes one setting, the rest of `config.yaml` stays byte for byte as it was. Go re-encodes the whole file. Its v0 setters write it from typed values, which turns YAML 1.1 booleans such as `yes` and `on` into `true`; since v8.0.35 its v8 config API re-encodes the parsed document instead, which keeps such values as written but rewrites every non-empty flow collection in the file as a block and unquotes double-quoted keys; cliproxy-rs writes the values it changes that way and leaves untouched flow collections such as `api-keys: [a, b]` as they are. One exception: a v8 JSON write of a float to a setting that is not a string saves the parsed number (`1e3` into `server.port` saves `1000.0`) where Go saves the body's text (`1e3`); both load the same value into that setting.
- Config writes, management key: a plaintext `management.secret-key` written through the v8 config API is stored as its bcrypt hash in the same write, and the reply's `ETag` names that file. Go v8.0.35 writes the plaintext, and its background reload after the save then hashes it and rewrites the file, so the plaintext stays on disk until that reload runs. Here it never reaches `config.yaml`.
- Config writes, body upload: a v8 config write (`PUT`, `PATCH` or `POST` under `/v8/management/config`) checks the stored file, its `If-Match` precondition and the stored config's parse under the config lock, as Go does before it reads the body, then releases the lock while the body arrives and repeats those checks under the lock before it writes. Go holds its lock through the upload, so a slow client delays every other config save; in cliproxy-rs another save can land while a body is uploading, and the write then answers `412` (with `If-Match`) or applies to the newer file.
- Config YAML, tags and anchors: the config load reads tagged scalars as yaml.v3 does: a `!!binary` scalar (and its aliases) is its base64-decoded text, a scalar with an unknown local tag (`!keep x`) is its text, a plain scalar with the non-specific `!` tag is null when it spells null and otherwise its own text, and the literal short tags `!<!!binary>`, `!<!!null>` and `!<!!str>` act as the standard ones. It refuses to load, where Go loads, a file with: a `!!binary` value whose bytes are not UTF-8 text (a setting holds a Rust string; Go stores the bytes); an explicitly tagged mapping key, whatever the tag (`!!str <<:` is an ordinary key in Go, not a merge), an aliased mapping key, or a mapping or sequence used as a key (Go rejects those too); a quoted `<<` key (`'<<':`, `"<<":`, an escape such as `"\x3c<":` or a block scalar), which Go reads as an ordinary key and cliproxy-rs would merge; a merge source that an explicit key or an earlier merge source shadows but is not a mapping or a list of mappings, such as `server: {port: 1}` beside `<<: {server: {<<: 5}}` or a `<<: *s` there naming a sequence (refused with Go's `yaml: map merge requires map or sequence of maps as the value`; Go never decodes a shadowed merge source and loads `server.port` 1); a non-specific `!` tag on a plain value that does not start with a letter or is a boolean word (`! 8317`, `! ---`, `! yes`), since telling those apart would need a YAML resolver Go and cliproxy-rs do not share, or another literal short tag on a scalar such as `!<!!int> 1` (on a mapping or sequence any tag is read by its kind, as in Go); a `%00` anywhere in the source of a tagged node or of a document's directives (the YAML library cliproxy-rs uses cuts a tag at the NUL, Go keeps it); and an anchor name defined twice (the YAML library binds an alias of a redefined anchor to a different node than Go does). Preparing a file for a remote store reports the same refusals, the management config routes, which read the file the same way, answer `500 invalid_config` while the file on disk is one of them (Go can serve such a file's YAML and JSON views and accept writes to it), and a body sent to `PUT /v0/management/config.yaml` with a quoted `<<` key is refused with `400 invalid_yaml`. Go accepts it and never merges it: a legacy-layout body is saved as sent (apart from its comment indentation) and loads the quoted key as an ordinary key (`"<<": {port: 1}` loads with port 0); in a v8 or mixed-layout body, Go's layout normalization comments the key out as an unrecognized section (`server: {"<<": {port: 1}}` is saved as `server: {}` and a `# "server.<<": {port: 1}` comment). It also refuses a plugin's `plugins.configs.<id>.store.version` or `store.release-tag` given as a `!!binary` value, directly or through an alias or merge, even when an explicit key or an earlier merge source overrides that value (`store: {<<: *d, version: !keep 4.5.6}` with a `!!binary` version in `d` is refused, where Go pins 4.5.6): Go reads the pin from the raw node, so it keeps the base64 text, fails the version grammar and leaves the plugin unpinned, where the decoded text would pin it.
- Plugin configs: a plugin gets its `plugins.configs` entry, in Home mode too, written so that each value reads back as Go's `runtimeConfigYAML` hands it over, into `any` or into a string: a plain scalar keeps its YAML text (`1.50`, `1e3`, `0x1F`, `007`), an `!!int`, `!!float`, `!!bool` or `!!timestamp` tag stays (`!!float 1.50`), and aliases and merges are expanded. Go marshals the raw node; cliproxy-rs writes block YAML with every string double-quoted, so comments, quoting and flow styles are not kept, `!!str`, `!!binary` and `!!null` scalars are written as their value, and a local tag on a scalar is dropped (`!keep 1_000` arrives as the string "1_000", which is what Go's node gives too); on a non-empty collection the tag is written. Mapping keys are written from their parsed value: `1.50:` arrives as `1.5:`, `007:` as `"007":`, and plain `1_000:` and `2001-12-14:` keys as strings where Go has an int and a time. The extra read that keeps this text counts each alias copy of a plugin scalar that is not plain text toward the 1,048,576 alias-copy limit; a config past it, which the load itself accepts, gives every plugin its parsed values (`1.5` for `1.50`) and logs a warning.
- Config YAML, tagged numbers: a scalar tagged `!!int` or `!!float` whose text the YAML library cliproxy-rs uses does not read as that type, such as `!!int 007`, `!!int 1_000`, `!!int 0X1F` or `!!float 1_0.5`, refuses the file with that library's `invalid value` error. Go loads it: yaml.v3 reads it into a string setting as its text and resolves it into a number setting.
- Config YAML, integers beyond 64 bits: a plain integer outside int64 and uint64 that fits 128 bits reads as yaml.v3 reads it (a decimal one as a float, `0x…`, `0o…` and `0b…` as text, a string setting as its text). Still refused where Go loads the file or body: such an integer with a local tag (`!keep 18446744073709551616`); two such mapping keys that round to the same float (`duplicate entry`); one used as a key of a config map (`config keys must be strings`; Go uses its text); and a negative one in an int setting (`-100000000000000000000`, which Go stores as the minimum int64). Where a save writes a section out again (migrating a legacy-layout file to the v8 layout, or archiving an unknown key as a `# key:` comment), such an integer is written as its float (`1.8446744073709552e19`) or quoted (`'0x1FFFFFFFFFFFFFFFFF'`), so a string setting or a plugin reading the saved file gets that text, where Go keeps the integer's text.
- Config YAML, alias copies: a file whose aliases copy more than 1,048,576 scalars that the load reads as yaml.v3 does instead of as its YAML library does (`!!binary` and other tagged values, and numbers or booleans such as `0x1F` in a string setting) is refused with `config YAML aliases expand too far`. Scalars written in the file do not count, and neither do copies of an anchored list into a position outside any anchored list or mapping. Alias copies of numbers or booleans that land inside an anchored list or mapping do count, even when no alias puts them in a string setting. Go refuses a file with many aliases compared with its size as excessive aliasing (`yaml: document contains excessive aliasing`), so it refuses `x: &x [0, …]` with 1,025 numbers and `y: &y [*x, …]` with 1,024 aliases of it (7 KB) too, but loads the same lines beside about 600,000 padding numbers (1.8 MB), which cliproxy-rs refuses. It also loads a large file whose aliases make that many copies outside anchors, such as 600,000 padding numbers beside 1,050 `oauth.excluded-models` channels that each alias a 1,000-number list. Aliases may also visit at most 4,194,304 anchor entries in all, kept as copies or not (a number an alias puts outside any string setting is dropped), and a file past that is refused the same way. Go refuses those files too, as excessive aliasing, whatever key the aliases sit under, including keys the config does not read: 2,048 aliases of a 2,049-number list under an unknown root key fail in Go in milliseconds. In the Management API, a YAML upload over either limit is refused with `400` and `config YAML aliases expand too far`, and while the file on disk is over one the v8 management config routes answer `500 invalid_config`, where Go serves any file it loads.
- LAN discovery without interface filters on the command line (`cliproxy discover`, `-discover`): cliproxy-rs reads `discovery.interfaces` from `config.yaml` with the config decoder, so a file it refuses makes the command exit 1 with the refusal instead of scanning. That covers invalid `!!binary` data anywhere in the file, a merge of something other than a mapping (`<<: 5`, or an alias of a sequence, which Go's decoder also fails) and the restrictions under "Config YAML, tags and anchors". Go decodes only the discovery section and scans: with no filters when that section fails to decode (`include: [!!binary '!!!']`), with the file's filters when the problem is elsewhere (invalid base64 under `proxy-url`). A missing file or a YAML syntax error scans with no filters in both.
- Config YAML, saved `!!binary` values: management saves keep the text of each `!!binary` scalar they do not change. Where a save writes a setting out again, as a v8 write does when it migrates a legacy-layout file to the v8 layout, the value is saved as its decoded text without the tag; Go moves the tagged node. The saved value is the same. A `GET /v8/management/config.yaml` of a legacy-layout file shows such a value in the migrated sections as its decoded text, where Go shows the tagged node.
- Config YAML, saved numbers in string settings: a management write that re-emits a section saves a string setting written as a plain number or boolean quoted (`'1.50'`, `'0x1F'`, `'True'`, `'007'`). Sections are re-emitted when a legacy provider-key section is migrated to `api-keys`, when the comment-preserving migration cannot move a legacy layout, and when the file cannot be edited in place, in which case a v8-layout file is written out again whole and quoted too. The loaded value is Go's, but the v8 JSON view then answers the string (`"1.50"`) where Go, which keeps the plain node, answers the number or boolean (1.5). A `GET /v8/management/config.yaml` of a legacy-layout file likewise shows those settings in the migrated sections quoted, where Go shows them plain. A v8 JSON write (`PUT` or `PATCH`) that sets a string setting to a number whose text the save would not write back as it is (`1.50`, `1e3`) also saves it quoted, as its text, which loads as Go's value, and the v8 JSON view then answers the string (`"1.50"`) where Go answers the number (1.5); a number it writes back as it is (`5`) is saved plain, as in Go.
- Config YAML, `client.codex.web-search-result-cache`: Go's custom unmarshal and `Validate` refuse values that cliproxy-rs, which checks the section only against its Go field types, accepts: a `ttl` of `0x1F`, `abc`, `yes`, `"true"`, `'1.50'`, `1e3` or `-5` (Go takes only a plain string or integer that parses as a non-negative duration or seconds); an `enabled` of `yes` or `on`, read as true (Go takes only a YAML boolean); a `limit` of `1.5`, read as 1, or `-1` (Go takes only a non-negative YAML integer); and an unknown key inside the section, which Go fails on load and cliproxy-rs loads (its strict writes and the v8 migration treat it as Go does). Where Go fails the load or the management write, cliproxy-rs loads or saves. The setting has no effect in cliproxy-rs yet: the web search result cache is not ported.
- v8 config writes, decode error text: where Go's `PUT`/`PATCH /v8/management/config...` refusal is yaml.v3's typed-decode error (``parse config payload: yaml: unmarshal errors:\n  line 11: cannot unmarshal !!str `bad` into int``, the strict decode's `field unknown not found in type registry.CatalogSources`, or a custom decoder's wrapper around one, such as `parse plugin enabled: yaml: ...`), cliproxy-rs names the setting instead (`parse config payload: config.server.port has an invalid type`, `unknown setting config.models.unknown`), with the same status and error code. Go's line numbers count lines of its own re-marshaled candidate, and its type names are Go's. Other refusal messages are Go's text, apart from the refusals listed elsewhere in this file.
- `multimedia.disable-image-generation` given as a number (`disable-image-generation: 1`): cliproxy-rs refuses it (`config.multimedia.disable-image-generation has an invalid type`). Go parses the number's source text like a string, so `0` and `1` select off and on, and `0x1` or `1.0` fail with `invalid disable-image-generation value "0x1" (allowed: true, false, chat, passthrough)`; the parsed value no longer tells those apart. Booleans, null and strings are read as Go reads them, with its error text.
- Management key hashing, rewritten file: when a plaintext `secret-key` cannot be replaced in place (it is shared through a YAML anchor or merge, or its node cannot be edited), Go rewrites the whole alias-expanded document and keeps each scalar's text. cliproxy-rs writes the expanded tree from parsed values without tags, so it refuses the rewrite when the document has any explicit tag (`!!binary`, `!!str`, a custom tag, the secret's own included), any mapping key that is not a string (`0x1F:` would become `31:`), or any other scalar whose text would change (an unquoted `0x1F` would become `31`, `0.50` would become `0.5`). Preparing a file for a remote store then fails with `rewriting the config file would change the text of another setting`, where Go uploads the re-encoded file (for example a merged secret beside `server.host: !!binary ...` or a hex key) or refuses because the plaintext is still present; an ordinary startup keeps the hash in memory and leaves the file as it is, as it does on a read-only mount.
- Management key hashing, tag directives: preparing a config file for a remote store refuses with `the management key's YAML tag cannot be resolved for upload` when the `secret-key` value is tagged and the file has a `%TAG` directive, or the tag uses a named handle. Go resolves the handle (so `%TAG !e! tag:yaml.org,2002:` makes `!e!binary` a base64 secret, and `%TAG !! tag:example.com,2000:` makes `!!binary` an ordinary string) and prepares the file. The same refusal applies when the `secret-key` value is reached through an alias, a merge or an aliased section and the file has any tag that is or could be the binary tag: Go follows the alias to its tagged target and decodes it, and cliproxy-rs does not resolve that. Shorthand and verbatim tags with `%XX` escapes, and tags that resolve to the short spelling `!!binary` (`!<!!binary>`, `!%21binary`), are resolved as Go does.
- Management key hashing, Unicode line separators: preparing a config file for a remote store refuses any file that contains U+0085 (NEL), U+2028 or U+2029, with `the config file contains a Unicode line separator yaml-edit cannot read`. yaml.v3 ends a line at those characters, and the syntax tree cliproxy-rs edits through does not, so a comment ending in one would hide the next line from the secret's tag check. Go prepares such a file, including one where the character is only string content.
- Watcher: when a config change moves `auth-dir`, cliproxy-rs starts watching the new directory. Go keeps watching the old one until it restarts.
- Watcher, where file change notifications cannot be set up (inotify instance or watch limits on Linux, the descriptor limit on macOS, or an operating system other than Linux, macOS and Windows): cliproxy-rs logs one warning and checks the config file and auth files every 2 seconds instead. Go stops at start: with `cliproxy: failed to create watcher` when the inotify or kqueue instance cannot be created (or the OS has no fsnotify backend), and with `cliproxy: failed to start watcher` when the config file or auth directory cannot be added. On FreeBSD, OpenBSD, NetBSD, DragonFly and illumos/Solaris, Go reloads from kqueue or FEN events, while cliproxy-rs polls every 2 seconds. As in Go, changes made by another machine on a network or FUSE file system can go unreported until the next local change: on NFS, 9p (such as WSL2's /mnt/c) and sshfs they are not reported, and on SMB/CIFS shares they may not be, depending on the server (on Windows, ReadDirectoryChangesW asks the server for change notifications, which SMB 3.0 servers can send).
- Watcher, symlinks: cliproxy-rs also watches the folders that hold symlinks on the way to the config file, the auth folder and symlinked auth files, so a Kubernetes Secret update (the `..data` swap) or an `ln -sfn` to a new release folder is reloaded. Go's fsnotify watches only the config file and the auth folder and misses those.
- Token refresh: the refresh loop sleeps until the next token is due and looks again at least every 10 minutes of awake time while any credential can come due. Go looks every 30 seconds. After a computer wakes from sleep or the clock jumps forward, a token that expired in the meantime is refreshed by the first request that gets a 401 (one extra round trip; the other credentials are refreshed about a second later) or within 10 minutes.
- Model catalogs: outside Home mode, the default source of the Codex client catalog (no `models.codex-catalog` and no `--local-model`) is first read when a Codex credential exists, a Codex client asks for `/v1/models?client_version=...`, or a Codex client sends a Responses request with `client.codex.optimize-multi-agent-v2` on; that of the Devin catalog when a Devin credential exists; and the Antigravity client version (the Antigravity Hub updater manifest every Antigravity user agent carries) when an Antigravity credential exists. Go starts all three at launch and refreshes them every three hours whether or not they are used. An explicit source, `--local-model` and the models.json catalog start at launch, a config reload that changes a catalog's source switches it at once, and in Home mode the Codex catalog and the Antigravity version start at launch, all as in Go. `--local-model` does not keep the Antigravity client version local, as in Go. Until the first manifest download, Antigravity requests carry the built-in fallback version, as Go's do until its first download finishes. Until the first Codex catalog read, Codex client catalog answers and the `spawn_agent` model lists use the catalog built into the binary; after it, they match Go. Until the first Devin catalog read, the Management API's model definitions for the `devin` channel list the Devin catalog built into the binary, so outside Home mode they stay that catalog until a Devin credential exists; Go lists the downloaded one.
- Model catalog reads: a remote catalog source (an http(s) `models.catalog`, `models.codex-catalog` or `models.devin-catalog`, or the router-for-me default) is read with a 30-second bound on the request, its redirects included, and a separate bound on the body of at most the time that was left. Go reads it through `http.DefaultClient`, which has no timeout, so a stalled source holds that catalog's updater until its source changes or the process stops. Both use the environment proxy, not `proxy-url`. The URL and every redirect hop are built as Go's `net/url` builds them: the source is parsed as `url.Parse` parses it, each redirect `Location` is resolved with `URL.Parse`, and each request is sent with `URL.RequestURI`, so dot segments stay as written and the path is escaped as Go escapes it (`/my catalogs/../m.json` is requested as `/my%20catalogs/../m.json`, `/a%2Fb/x|y.json` as `/a/b/x%7Cy.json`). A source Go fails to parse or that has no host, and a redirect whose `Location` Go fails to parse or whose resolved URL has no host, fail the read in both. cliproxy-rs refuses, where Go reads the source: a non-ASCII host (`https://bücher.example/...`) or a host with a percent escape, which includes an IPv6 zone (`http://[fe80::1%25en0]:8080/...`), in the source or in a redirect; a host the WHATWG URL parser that routes each request rejects, such as one whose last label is a number but which is not an IPv4 address (`http://catalog.internal.1/m.json`) or one with an `xn--` label that is not valid IDNA (`http://xn--a.example/m.json`), which Go resolves through DNS, in the source or in a redirect; a port Go writes in the `Host` header that the HTTP library would leave out: the scheme's default port written out (`http://h:80/m.json`, `http://h:080/...`, `https://h:443/...`) in the source or in a redirect, and an empty port (`http://h:/m.json`) in a redirect (Go drops an empty port in the source, and so does cliproxy-rs); a request target the HTTP library does not carry as written, such as a query holding a space, `"`, `<` or `>`, or a URL longer than 65,534 bytes; and a redirect whose `Location` is not valid UTF-8, which is not followed: the 3xx answer fails the read, where Go follows it. Each of these counts as a failed read and keeps the last valid catalog.
- v0 setters over a refused file: a deprecated `/v0/management/...` setter edits `config.yaml` as it is on disk and validates the result. When the file holds a setting a reload refused, such as a relative `models.catalog`, the write answers `422 invalid_config` with that setting's error and the file stays as it is; the running config keeps the last valid values. Go marshals its valid in-memory config over the file and saves, which replaces the refused value with the running one.
- v0 `config.yaml` uploads with several errors: the upload checks the model catalog sources before it decodes the setting types, so a document that also holds a mistyped setting or a nonnumeric legacy weight can name the invalid source where Go names its YAML decode error first. Both answer `400 invalid_yaml`; for example `models: {catalog: [bad], devin-catalog: relative.json}` names the `models.devin-catalog` source here, where Go reports `yaml: unmarshal errors:` with `cannot unmarshal !!seq into string`.
- Remote model catalogs: a refreshed `models.json` is refused whole, and the catalog in use is kept, where Go would decode it differently from the members cliproxy-rs keeps. That happens when a section (`claude`, `gemini` and the others), a model field, a `thinking` field, `config.override_header` or a `native_capabilities` field is named in another case, or appears more than once in the same object, case-folded. It also happens when an integer field holds anything but an integer literal. Go matches those names case-insensitively and decodes repeated members one after another into the same field, so it serves `{"thinking":{"Min":1}}` with `min` 1 and `"inputTokenLimit":1,"InputTokenLimit":2,"inputTokenLimit":3` as 3. It merges a repeated `thinking` object and serves a lone `GEMINI` section as `gemini`. Go refuses fractions such as `0.0`, `-0.0` and `1e-400`, and accepts `-0` as 0, as cliproxy-rs does. A refresh also refuses `"type":null` and `"thinking":{"levels":[null]}`, which Go serves as `"type":""` and `levels: [""]`. Model IDs are validated as Go decodes them. Go likewise keeps the previous catalog when no source decodes.
- Watcher startup: cliproxy-rs reads `config.yaml` once when the watcher starts, so an edit made after the config was loaded but before watching began takes effect. Go starts watching without rereading the file and keeps the older config until the next edit.
- Management JSON bodies: credential status, plugin enable, `/requests/api-call`, the OAuth callback `POST` and the Sign in with ChatGPT bind read the first JSON value and match member names the way gin's `ShouldBindJSON` does, and skip unknown members unread, as Go does. A member that names a string field and holds invalid UTF-8 or a lone surrogate escape (`"\ud800"`) answers that handler's invalid-body 400; Go binds it with U+FFFD in place of each bad byte or surrogate. `PATCH /credentials/fields` decodes its values as Go does, invalid text included. It refuses two kinds of value with 400 `invalid field <name>`: a number outside float64's range (`1e400`), and a value nested more than 127 levels deep, counting the file's root object and the objects a dotted field path creates, even around a scalar. Go writes both. It then cannot load the first kind (its float64 decode fails), and cliproxy-rs's auth loader cannot load the second.
- Auth file saves from the Management API (credential status and fields) write the bytes Go's file store writes: `json.Marshal` of the metadata, so keys are sorted at every level, `<`, `>`, `&`, U+2028 and U+2029 are escaped, and no newline follows. Numbers are written as Go holds them in memory, which depends on what the record was built from, not on the file as it is now. For a record loaded from a file, that is Go's float64 reading of the loaded text, correctly rounded as `strconv.ParseFloat` rounds. A number a fields patch sent, the `request_retry` integer and a `headers` value that is not a string map are written as sent, or for `request_retry` as the exact integer, and keep that form in later saves until the file reloads, as Go keeps them in memory. If the file was changed after it was loaded and has not been reloaded yet (including the moments between start-up and the watcher's first reload of an edited file), cliproxy-rs no longer has the loaded text: integers are still exact, but a record holding any other number that the save does not replace is refused with `500` `{"error":"failed to update auth: Io(\"the auth file changed since it was loaded; retry after it reloads\")"}`, and neither the file nor the record changes. Go saves it from the text it loaded. Like Go's flag, `disabled` is always the record's boolean. A save whose document equals the file's, numbers compared as float64 so that `0` equals `-0`, writes nothing: the file keeps its inode and modification time, and the saved record is published all the same, as Go's manager publishes it. For a Codex login file the disk's credential fields win, as in Go's `PersistCodexAuthFile`. A save whose result the auth loader could not read back (serde reads 127 levels of nesting; Go's decoder reads 10,000) is refused with `500` `{"error":"failed to update auth: Io(\"the saved auth file could not be read back\")"}`, and neither the file nor the record changes. Fields patches refuse such values with `400` before this point (see Management JSON bodies), so this answer comes only from a Codex save that imports a deeper `siwc` subtree written to the file since it was loaded. Go saves it. A record whose provider or metadata `type` is `codex`, token-less ones included, is saved under its file's credential lock (`<name>.lock`), as in Go. Go also writes a record that still holds the token storage of a login made in the same process through that storage's own encoding. cliproxy-rs has no such record: a login is saved once, and later saves start from the file.
- Codex credential locks in the Management API: a credential status or fields save, an upload and a Sign in with ChatGPT binding of a Codex record (provider or metadata `type` `codex`, token-less ones included) take the file's credential lock (`<name>.lock`), as Go's store and `BindCodexSIWC` do; deletes take none, as in Go. While another holder has the lock, such as a token refresh in this or another process, the write waits for it without holding up other management writes or the watcher. An upload is written as sent before the wait, as in Go, and then saved under the lock as Go's store saves it: the file's credentials merged in, its `disabled` flag set and `json.Marshal` written unless the file holds exactly those bytes, so tokens a refresh wrote during the wait are kept. If the lock file cannot be opened (for example, a directory has its name), cliproxy-rs refuses a status or fields save with `500` and changes nothing; Go logs the failed save and answers `200`, with the change in memory only. An upload has by then written the file as sent in both: cliproxy-rs answers `500` (a multipart upload lists the file as failed) and publishes nothing until the watcher loads the written file, where Go logs the failed save, answers `200` and registers the upload at once. A binding fails in both.
- Saves of a deleted auth file: a credential status or fields save from the Management API whose saved record is disabled writes the credential's file again when it was deleted from disk since it was loaded, whatever the provider, with its `<name>.lock` for a Codex record. Go's store skips the write for a disabled record whose file is missing (`FileTokenStore.Save`), so the change stays in memory.
- Shutdown and Codex token refreshes: a refresh that holds a credential file's lock finishes before the process exits, so tokens a grant returned are written to the file. Each grant attempt times out after 30 seconds, with up to three attempts per token set, so an unresponsive token endpoint can delay the exit by about 93 seconds per token set (three 30-second attempts and pauses of 1 and 2 seconds), about 3 minutes for a file with both its outer and its Sign in with ChatGPT tokens. Refreshes and management writes still waiting for a lock give up at once. Go does not wait for refreshes in flight, so a refresh token spent at exit can be lost.
- Auth file fields, numeric `use_siwc`: `PATCH /v0/management/auth-files/fields` refuses (400) a `use_siwc` number that is not a 64-bit integer, such as `1.5`, `1e0` or `10000000000000000000`. Go stores it, reads it as no flag (its `json.Number` fails `Int64`) until the file is loaded again, then as true when non-zero. Refusing it keeps the credential version that fences an in-flight token refresh moving exactly when Go's does.
- Management panel: cliproxy-rs never downloads or updates its dashboard; it is built into the binary. Go downloads its panel from `management.panel-github-repository` when it is first requested and checks for a new one every three hours unless `management.disable-auto-update-panel` is set. cliproxy-rs accepts both settings, checks their types and keeps them in `config.yaml` (setting `panel-github-repository` to null through the Management API stores null, as Go v8.0.35 does), but nothing reads them. `management.disable-control-panel` still turns the built-in dashboard off.
- Sign-in errors: when a Codex, Kimi, Meta, xAI or Devin sign-in started from the Management API fails, the session error keeps Go's message, status and OAuth error code but leaves out upstream response bodies, OAuth error descriptions and decoder details. Go copies those in, and they can contain tokens, while the callback route shows session errors to anyone who holds the session state without a management key. For example, a failed Codex code exchange ends at "token exchange failed with status 400" where Go appends the response body.
- Masked keys in logs: Go masks API keys, tokens and secrets in request logs and query strings by keeping a few bytes at each end, but leaves a value of one or two bytes unchanged. cliproxy-rs writes `...` for those, so a short client key never appears in a log.
- AI Studio relay credentials in the Management API: a browser connected to `/v1/ws` is listed as a runtime-only credential. Its `created_at` is the time the Management API first listed it, and `updated_at` and `modtime` are the time it first listed the current version of the credential, so a status or fields edit moves them and a request does not. Go sets both when the browser connects and moves `updated_at` after every request result. The cliproxy-rs credential store keeps no timestamps.
- Deleting an AI Studio relay credential through `DELETE /v8/management/credentials` (or the v0 `auth-files`) answers 404 "auth file not found" and touches nothing on disk. The credential has no file, so Go falls back to `auth-dir/<ID>`: if a file of that name exists, Go deletes it and removes the credential as well.
- Cookies in request logs: Go writes `Cookie` and `Set-Cookie` values to request logs and forced error logs unchanged. cliproxy-rs writes `<redacted>` for the whole value of any header whose name contains `cookie`, in the client and upstream sections alike, because a session cookie is a credential. The headers sent upstream and back to the client are unchanged.
- Upstream URLs in request logs: Go writes the upstream URL of each captured request as it is, so credentials in a configured `base-url` reach the log. cliproxy-rs writes `<redacted>` in place of any `user:password@` part and masks sensitive query values (`key`, and names containing `api-key`, `apikey`, `api_key`, `token` or `secret`) the same way it masks the client URL. Requests still go to the URL as configured.
- Usage records for a canceled xAI request: when the client goes away while an xAI HTTP request is in flight, the failure record says `context canceled` with status 499, as in Go, but leaves out the method and URL that Go's text adds when the cancellation hit the send (`Post "<url>": context canceled`). A configured base URL can carry credentials in its query.
- A client that goes away mid-stream from a Gemini API key, Gemini Interactions, Vertex or Antigravity stream: the usage record is Go's (a failure with status 499 and `context canceled`; on Vertex and Antigravity a success once a terminal chunk went out, and on Antigravity the failure keeps the usage seen so far). Go's credential result is a race: its stream wrapper records a failed result (counted in the credential's failures and recent requests; `context canceled` never starts a cooldown) only when it receives the executor's error chunk before it sees the cancellation, and otherwise records nothing. cliproxy-rs always reports the attempt as cancelled, which counts as neither a success nor a failure and leaves availability unchanged. Go's Gemini, Interactions and Vertex executors have the same race: a cancellation that finds one handing a chunk to the client, not reading upstream, ends quietly and publishes a success; cliproxy-rs treats every drop before the end as the read case. (Go's Antigravity executor fails in both cases, as cliproxy-rs does, but counts the terminal chunk only once the client took it, where cliproxy-rs counts it once it is produced.)
- xAI request logs: the API REQUEST section of an xAI video status poll says `HTTP Method: GET`, the method sent upstream. Go logs every xAI request as `POST`, including that `GET`.
- OAuth callback: the unauthenticated `POST /v8/management/oauth/callback` (and the v0 `oauth-callback`) accepts a body of at most 64 KiB; a larger one gets `413` with the handler's `{"status":"error","error":"invalid body"}`, its answer when `server.max-request-body-bytes` stops the read. Go has no route-specific cap there; only its configured global `server.max-request-body-bytes` applies, as it does in cliproxy-rs. Real callbacks are a few hundred bytes; the limit protects servers reachable from the internet.
- Responses WebSocket: when a continuation pinned to its credential fails with 401 or 429, the client is always closed with 1012 (replay over HTTP). In Go, the same error also closes the upstream socket, and the disconnect watcher can close the client first with the error instead of 1012.
- Session affinity: a request without a session ID whose body nests more than 128 arrays and objects is not matched against earlier conversations by its messages; it keeps the session identity derived from its instructions and first user message, as a request without a client key does. Go matches it at any depth on its growable stacks, while the same walk on a native stack overflows and stops the server. Real conversations nest far less.
- Session affinity: when a routing change (strategy or a `session-affinity` setting) replaces the conversation matcher, its access counter keeps counting. In Go the new matcher starts again from zero, so a request picked before the change that fails afterwards can remove a conversation bound after the change, which loses that account until the next request binds it again.
- Request logs: when a logged body has a malformed Brotli encoding, cliproxy-rs can leave out the partly decoded bytes that Go writes to the log, and the decoder's error text differs from Go's. Well-formed compressed bodies are logged as in Go.
- Kimi, Meta and Devin request logs: when an upstream request fails before any response arrives, the `Error:` line of the API RESPONSE section has cliproxy-rs's own message, such as `upstream request failed`, where Go writes its HTTP client's error (`Post "<url>": ...`). An error response from Kimi or Meta is logged up to its first 16 MiB, the part cliproxy-rs reads; Go logs the whole body. When a Kimi or Meta stream ends with a read error and also fails the apply_patch end check, the log keeps the read error, which Go leaves out in that case.
- Vertex service-account imports (`-vertex-import`, `oauth/import?provider=vertex` and `/v0/management/vertex/import`) write the credential atomically with mode 0600, because it holds the account's private key. Go creates it with `os.Create`, which gives 0644 under the usual umask.
- Gemini, Vertex and Antigravity streams: when the upstream ends a stream's body early (before its length or final chunk), the stream fails with `unexpected EOF`, as Go's scanner reports it. A reset or timeout in the middle of a stream reads as `upstream request failed`, where Go shows its transport's error text, which can name the upstream URL.
- Devin request logs: the end-of-stream summary (thinking, content and signature) is collected only when `request-log` is on as the stream starts, so a stream nobody logs is not kept in memory. A stream that is already running when `request-log` is turned on gets no summary; Go collects one for every stream.
- Codex token refresh errors: when the token endpoint refuses a refresh of a Codex credential's Sign in with ChatGPT tokens, the error message keeps the upstream status and the OAuth error code, as in `OpenAI OAuth token request failed (400): refresh_token_reused`, and leaves out the rest of the response body, which Go appends; that endpoint is sent the refresh token. The error's own status is remapped as for the outer tokens: a refused grant (400 to 403) answers 401 and any other status 502.
- Codex token refresh of a plugin-virtual credential (one of several Codex credentials a plugin parsed from one file): cliproxy-rs refreshes it in memory without taking the file's credential lock, reading the file or writing it, so the plugin's file is left as it is. Go locks and reads that file, can adopt the tokens at its top level, and writes the refresh back into it with `json.Marshal`, which re-encodes the whole plugin document and rounds integers above 2^53. Go then replaces the credential's metadata with the plugin document's top-level fields, and its merge deletes keys that document lacks, so a credential whose tokens are not at the document's top level can lose them; cliproxy-rs keeps them.
- Codex token refresh of a file holding invalid UTF-8 or a lone surrogate escape (`"\ud800"`): cliproxy-rs reads the credential file as strict JSON under its lock, so such a file fails the refresh before any grant, and a file another writer left that way while a grant ran fails the write, and the new tokens are lost. Go reads both with U+FFFD in place, refreshes and writes the new tokens.
- Codex token refresh results: a successful refresh of a Codex credential's outer tokens or its Sign in with ChatGPT tokens is kept for five minutes and handed to any refresh that starts from the same refresh token in that time, so a stale copy of the credential cannot send a rotated refresh token again (the endpoint answers `refresh_token_reused`). A failed outer refresh is kept for five minutes too, as a backoff; a failed Sign in with ChatGPT refresh is not kept, so a retry reaches the endpoint. Go shares only refreshes that are still running and forgets each result when it completes.
- Codex Sign in with ChatGPT expiry: a JSON number in the `siwc` partition's expiry fields or in its access token's `exp` claim is read through serde_json's float parse, which can differ from Go's correctly rounded parse in the last bit for a value with more than 17 significant digits. A value that close to the 1e12 boundary between Unix seconds and milliseconds can then be read in the other unit: `1000000000000.9999` is a time in 2001, so the token refreshes, where Go reads the year 33658. Token issuers write whole seconds. An `exp` claim whose value is a string with invalid UTF-8 or an unpaired surrogate escape makes the whole payload unreadable, so no expiry is taken from the token; Go reads that string with U+FFFD in place and still uses a later `exp` member (any case) of the same payload, so the refresh decision can differ for such a token.
- `--siwc-bind`: the callback listener binds only the loopback address, which is the address in the redirect URI. Go listens on every interface. With a remote token store (PostgreSQL, Git or object storage), cliproxy-rs also saves the bound credential file to the store after a successful bind, and only that file. Go writes the bound file only into the local auth directory, so the next start from the store does not have the binding. The credential lock file (`<file>.lock`) is the same in both, so a Go or cliproxy-rs `--siwc-bind` waits for a Go refresh of that file. A cliproxy-rs refresh of a Codex credential file takes the same lock, from before it reads the file until it has written the result.
- Codex live request logs: in the logs of `POST /v1/live`, `POST /v1/realtime` and `POST /v1/realtime/calls`, the ICE credentials of SDP bodies (`a=ice-ufrag:` and `a=ice-pwd:` values, also inside JSON or multipart bodies) are written as `[REDACTED]`, in the downstream and upstream sections alike. Go logs those bodies unchanged. The bytes sent to the client and the upstream are not changed.
- `PUT /v0/management/config.yaml`: comment lines are unindented before the upload is checked, so the check sees the bytes that are written. Go checks the upload as sent and unindents while writing; when a `#` line sits inside a block scalar, Go can overwrite `config.yaml` with YAML that no longer loads and then answer `500 reload_failed`. cliproxy-rs answers `400 invalid_yaml` and leaves the file alone. Two answers differ from Go: a type mismatch such as `port: abc` is `422 invalid_config` (Go: `400 invalid_yaml`), and YAML syntax messages come from a different parser, so only the status and the error code match.
- Terminal UI (`-tui`):
  - Each reply goes to the tab that asked for it. Go hands replies to the active tab only, so a reply that arrives after a tab switch is lost (and an OAuth poll in progress never finishes).
  - While a text field has focus, every key except Ctrl+C goes to the field. Go still quits on `q`, switches language on `L` and changes tab on Tab while you type. On the password screen `q` and `L` keep their meaning while the field is empty.
  - The status bar sits on the last terminal row; Go leaves two empty rows under it.
  - Long lines are cut at the terminal edge: there is no horizontal scrolling (`h`/`l`). The cursor does not blink, and Ctrl+V does not read the system clipboard (a terminal paste works).
  - Adding a client API key sends `{"old": key, "new": key}`, which adds the key when it is missing. Go sends `{"old": null, "new": key}`, which its own server rejects with `400 missing fields`.
  - A delete or edit started on the Auth Files or API Keys tab acts on the item that was selected. Go resolves the list position again when you confirm, so a refresh in between can delete another file or change another key. API keys are addressed by position, so if a refresh moves the selected key the action is cancelled.
  - `-tui -management-base-url URL` is a pure client: it starts without a local config, store or Home bootstrap. Go loads them first, so it fails without a local config and waits in cloud mode.
  - `-tui -standalone` works without a management key in the config or `MANAGEMENT_PASSWORD`: its generated (or `-password`) password is accepted from loopback, also after a config reload. Go refuses every management request without a configured key, so its standalone TUI never connects then. The TUI connects to the address the server actually bound, so `port: 0` and IPv6 loopback work. A `server.tls` setup or a host that is neither loopback nor a wildcard address is refused with an error; in Go these fail after 30 connection attempts.
- `pprof`: the optional separate listener serves the index, `cmdline` and `symbol`, and CPU `profile` on Unix in builds with `--features cpa-server/pprof`. The profiler and symbol resolver dependencies are absent from default builds, published release binaries, the Docker image and CI's size-gate build. Profiles of the Go runtime (`heap`, `allocs`, `goroutine`, `block`, `mutex`, `threadcreate`, `trace`) have no Rust equivalent and answer `501` with a plain message; without the feature, `profile` answers `501` too and names the feature. Without the feature, `symbol` consumes POST bodies but returns only Go's `num_symbols: 1` header, with no resolved names, including shared-library names. With the feature, symbol lookup uses the symbols available in the executable, so an unstripped build gives more names. Symbol POST bodies and URL-encoded profile form bodies (POST, PUT and PATCH) are limited to the server's 64 MiB and a larger body gets `413`. Go reads symbol bodies without a limit and reads URL-encoded forms up to 10 MiB, ignoring a larger form so the query's `seconds` applies. Go's `FormValue` also reads `seconds` from a `multipart/form-data` body; cliproxy-rs reads only URL-encoded bodies, so a multipart `seconds` is ignored and the query applies. When a `Content-Type` repeats a parameter with conflicting values (`application/x-www-form-urlencoded; charset=a; charset=b`), Go's `mime.ParseMediaType` returns no media type, so Go ignores the body and uses the query's `seconds`. cliproxy-rs still reads the body. On Windows, the listener also retries the Winsock accept errors `WSAEMFILE` (10024), `WSAEWOULDBLOCK` (10035) and `WSAETIMEDOUT` (10060), with the same 5 ms to one second backoff. Go's `Errno.Temporary` does not cover these codes, so Go stops serving on them until the next config publication. After an accept error that is not retried, connections already open keep running in both. The next config publication then gives them up to five seconds to finish before it binds the listener again, and after a timeout it waits for a further publication. Go discards the failed server, so its next publication binds without waiting for those connections. Listener addresses require numeric ports: unlike Go, `:` and service-name ports such as `:http` are not accepted.
- WebRTC media relay for Codex live calls (`oauth.providers.codex.live-media-relay`): every Go build includes it, and the config turns it on. In cliproxy-rs it is an optional build feature (`cargo build --release -p cliproxy --features cpa-server/media-relay`); the release binaries and the Docker image are built without it, so calls negotiate media directly with the upstream. In a build with the relay, TURN servers reached over TCP or TLS are skipped with a warning, because the WebRTC library cannot gather candidates through them; TURN over UDP and STUN work. Candidate gathering for the upstream peer stops after 6 seconds and the call goes on with the candidates gathered so far, because the library never finishes gathering when a STUN server stays silent. Go waits until gathering completes or the request is cancelled, so a TURN server that takes longer than 6 seconds to allocate a relay address still contributes a relay candidate in Go but not in cliproxy-rs.
- Images multipart forms: the `/v1/images/edits` route and the image executors read a form as Go's `ReadForm` reads it from an in-memory body, which takes a line of 4,096 bytes or more without a newline as `bufio: buffer full`. When Go's images route reads the request body directly (request logging off), the last read also reports the end of the body, so Go accepts a final boundary line of exactly 4,096 bytes that ends the body without a newline, or reports `multipart: NextPart: EOF` for another such line. cliproxy-rs refuses both with `multipart: NextPart: bufio: buffer full`.
- A base URL that Go's URL parser refuses (Vertex and OpenAI-compatible routes, for example a percent-escaped host such as `https://%61iplatform.googleapis.com`): both servers answer 500 with Go's parse error, cool the model for that credential, and start no retry round. Go does not count the attempt as having reached an upstream, because nothing was sent. cliproxy-rs counts it as one, since it marks every statusless error that way. This matters only when several credentials fail on the same request: Go then reports the last failure that did reach an upstream (for example another credential's 503), while cliproxy-rs may report the parse error if it came last. A base URL that Go's transport refuses, because it has no host (such as `https:relay.example`) or no `http` or `https` scheme (such as `relay.example`), counts as an upstream attempt in both.
- `use_siwc` before `auth_kind` (7b0319fb): Go classifies a credential with a true `use_siwc` as OAuth before it reads `auth_kind`, so one carrying both `use_siwc: true` and `auth_kind: apikey` (for example `{"use_siwc":true,"auth_kind":"apikey"}` in metadata) is OAuth in Go and an API-key account here. Synthesized auth files never have this shape, since the synthesizer sets their `auth_kind` attribute to `oauth`, which both servers read first; only a credential without that attribute that carries both fields could.

## Antigravity

The Antigravity implementation was recorded from `6fecc6e`, plus these v8.0.27 changes: the Claude 5.5 models (Go e3abd9ae, c575291a, 6b037f61 and 8a945b3f), Claude 5.5's CAQS thinking signatures (9b9c2bdf and 174248ca), and backend errors and split payloads inside streams (4e4dede4). The target is now v8.0.35; the remaining changes are gaps, not approved exclusions. Other differences:

- Reasoning replay restores items one by one, as Go's sequential path does. Go also has a batch path for long histories, an optimization whose output its own tests compare with the sequential path's.
- The replay and signature caches, AI credits state and short per-model cooldowns stay in the process; Go can keep them in Home's KV store.
- A credential's web-search capability probe runs when the model registry first sees a new revision of the credential. Its previous hints stay until that probe finishes, and a config reload alone does not probe again.
- A negative retry delay in a 429 answer counts as zero.
- A token that expires within five minutes is refreshed through credential preparation before the request is sent, and the new token is saved; Go refreshes it inside the request. Two credential files with the same refresh token refresh separately; Go shares one refresh between them.
- The AI credits lookup queued after a token refresh ends after 30 seconds, the bound of a credential acquisition. Go ends it when the request or refresh that queued it ends.
- When an upstream 401 inside an AI credits attempt refreshes the token, the retry is sent without the credits flag.
- Pooled connections (`connection-pool.enabled`) are kept per credential ID.
- Tool declaration schemas are cleaned in one pass over the tools. When one tool object repeats the `functionDeclarations` or `function_declarations` key, only the declarations of the first occurrence are renamed and cleaned; Go edits by path, and its edits can land on either occurrence. JSON encoders do not repeat keys.
- A forged compaction capsule fails with cliproxy-rs's own error text, not Go's `json.Unmarshal` message.
- When Google's token endpoint refuses a sign-in code exchange or a token refresh, the error keeps the status and the OAuth error code (such as `invalid_grant`) and leaves out the rest of the response body, as for the other providers' sign-ins. Go shows the whole body, which reaches logs and client answers; that endpoint is sent the code, the refresh token and the client secret. A refused refresh reads `token refresh failed with status 400: invalid_grant`.
- An AI credits attempt, which runs on a credential selection had passed over, never ends a cooldown window or frees another request's probe of it, whatever its outcome: those stay with the window's own probe.
- Reasoning replay branch IDs come from a counter, not random bytes; they are only compared inside one process.
- Not ported from v8.0.27 yet: per-account model entitlements and their probe scheduling (Go 7e857c37, 9521fe29, ad381435, 091ff27f), committing the signature replay when the client disconnects after the final chunk (a4acc9f7; its usage record is ported), thought tokens in OpenAI `completion_tokens` (ab151f5d), no `tool_calls: null` in OpenAI stream deltas (dfe0a0ef), dropping trailing thought-only model turns (a2718314), Interactions session continuation (cbc4cd55), and replay logging and batch retry changes (17dc1b81, 40f4df07, 611ebba4).
- Further changes through v8.0.35 still need porting or assertion-level verification: cached-token usage in Gemini responses (912a038b), fallback client version 2.23.0 (8fb633c9), the expanded linear schema-sanitization matrix (b8d4e14a), SDK user-agent helpers (acaab599), and expired AI-credits negative-hint recovery (904ec710).
