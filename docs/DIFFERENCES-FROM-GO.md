# Differences from Go CLIProxyAPI

Where cliproxy-rs has a feature, it aims to behave exactly as CLIProxyAPI does at commit `6fecc6e`. This page lists the places where it behaves differently on purpose, and the one routing strategy it adds. Features that are not ported yet are listed under [Upcoming features](../README.md#upcoming-features) instead.

## Additions in cliproxy-rs

- Routing strategy `soonest-reset` (alias `reset-first`), experimental and opt-in: select the account whose weekly window resets soonest, until it cools down or reaches a limit, then move to the next. An account whose reset time is not known yet gets one probe request. Conversations bound to an account stay on it. Go has only `round-robin`, `weighted-round-robin` and `fill-first`, and reads `soonest-reset` as `round-robin`. The dashboard offers it only when it is connected to cliproxy-rs. See [MULTI-ACCOUNT.md](MULTI-ACCOUNT.md#routing-strategies).
- Codex connection reuse, opt-in: `oauth.providers.codex.chatgpt-keep-alive: true` makes the Codex client for `chatgpt.com` (the Chrome TLS fingerprint) keep up to 2 idle connections per host and proxy for 90 seconds and send later requests on them, several at once over HTTP/2. The ClientHello, the request headers and the proxy are the same, and connections never cross proxies. Off, the default, it does what Go does: a dedicated connection per request, closed with the response body (`helps/utls_client.go`). The setting applies from the next request after a config reload. Go starts with the key in the file and ignores it. A config edit through Go's v8 Management API moves the key into a comment, so the setting is off again when you return to cliproxy-rs; edits through Go's v0 endpoints keep it. Setting the key through Go's v8 API is refused, as for any key Go does not know.

- `worker-threads` (top level of `config.yaml`): the number of request threads, by default the smaller of the CPU count and two; see [CONFIGURATION.md](CONFIGURATION.md#worker-threads). Go sizes its scheduler by the CPU count. The key is read once at start from the `-config` file (`./config.yaml` by default), before a remote store or Home supplies a config; in a store's `config.yaml` or in the config Home supplies (the local `-config` file still applies) it has no effect, and those deployments set `TOKIO_WORKER_THREADS` instead. Go starts with the key present and keeps it through v0 Management API saves. Any v8 configuration write (PUT, PATCH or DELETE under `/v8/management/config`) turns it into a `# worker-threads: N` comment and logs `unrecognized configuration section "worker-threads" commented out during v8 migration`, and `PUT /v8/management/config.yaml` with the key answers `unknown v8 configuration section worker-threads`. When one config.yaml is shared with a Go server, set `TOKIO_WORKER_THREADS` instead.

## Deliberate differences

- Claude Code identity: a native Claude Code `User-Agent` at or above the measured baseline (2.1.280) within the same major version is forwarded to Claude accounts. Go forwards only patch releases of the baseline's 2.1 line, so Claude Code 2.2 and later would be sent as 2.1.280 and treated like a third-party client. A forwarded release newer than the baseline must send well-formed `X-Stainless-Package-Version` and `X-Stainless-Runtime-Version` headers, which go upstream with it; without them it is cloaked as 2.1.280, as before. Go replaces both headers with the baseline values, so its headers can disagree with the forwarded `User-Agent`. The Haiku helper requests of such a release (session titles, quota probes) follow the same rule while their measured beta and body shapes hold; Go confirms a helper only with the exact baseline tuple. When cliproxy-rs adds a billing block to a forwarded newer release, the block's `cc_version` is that release's version; Go uses the baseline's. With `stabilize-device-profile` on, Go's 2.1 patch rule applies unchanged, because a stabilized profile forwards only the exact baseline tuple; the Stainless requirement, the helper rule and the billing version above apply only without stabilization. A `claude-cli` `User-Agent` that is refused while the baseline identity is sent is logged at most once per credential and version (64 slots per credential, so two versions can share one line), naming the credential by its auth index.
- Thinking off on Claude models that refuse it: `reasoning_effort: "none"`, a zero thinking budget or `thinking: {"type": "disabled"}` sent to Claude Opus 5.5, Sonnet 5.5, Fable 5 and 5.1 or Mythos becomes adaptive thinking at effort `low`. These models answer 400 to `disabled` (Anthropic's thinking troubleshooting table), and Go sends `disabled`. Other Claude models still get `disabled`.
- Codex and xAI WebSockets: writing one frame upstream is bounded to 10 seconds, or to the frame's size at 128 KiB per second (rounded up) when that is longer. A write past the bound fails like any other write: if the upstream already closed the socket with 1009 (message too big), the request gets the same 413 as a failed write; otherwise the socket is dropped and the request is retried once on a new socket, or answered with a replay request on a continuation. On a steering (duplex) stream, a failed or timed-out write after the stream started ends the stream with that error. Go sets no write deadline, so a half-open socket held the request until the 300-second read deadline.
- Upstream connections: the Claude client for `api.anthropic.com` keeps every idle connection for 90 seconds. Go's transport for it keeps at most 2 idle connections per host (net/http's default) with no time limit, so after a burst of concurrent requests Go dials again and cliproxy-rs does not.
- Upstream timeouts: a request with a fixed timeout (Kimi and xAI sign-in and token refresh, the Codex and Devin model catalogs, the Management API `api-call`) gives all its redirect hops one deadline, as Go's `http.Client.Timeout` does. Reading the final response body is bounded separately, by the time that was left when its request was sent, so a slow body can stretch the exchange to at most twice the timeout. Go's deadline also covers the body.
- Quota cooldowns (`routing.cooldown.max-trusted-cooldown`, a bug fix, on by default): when an upstream answers 429 with a reset time (Codex `usage_limit_reached` with `resets_at`, Claude's `anthropic-ratelimit-unified-*-reset`, or `Retry-After` from any provider), Go rests the account until that time, even when it is days away, and never asks again. Providers often reset early, which leaves the account unused until the stated time or a restart, and with `save-cooldown-status` a restart restores the same wait. cliproxy-rs rests the account for at most one hour at first, then lets the next ordinary request through as a check (no timer or background request). Only that one request goes upstream: until it is answered (or for at most 30 seconds), other requests see the account as cooling, and retries never wait for such a window. Only the probe's own answer or cancellation ends the check: an answer or cancellation from a request picked before it, including an earlier probe whose 30 seconds ran out, neither frees the account nor opens the next window. A streamed answer counts as soon as its first event arrives, so other requests use the account while the stream runs. One exception: when one model of a pooled `openai-compatibility` model alias (several models under one alias name) has its own window (not the account's), requests for the alias that arrive together after that window ends can each probe that model, because the reservation is taken for the alias at pick time and the pool chooses its model later. Each window that ends in another 429 doubles the next, a success ends the escalation, and the rest never passes the stated reset except by Go's own additions: its 10-second minimum and the 1 to 30 seconds of random delay it adds to Claude's reset. A success from a request picked before the window opened (a stream that outlived the 429) leaves the window to its probe; Go clears the cooldown on any success. A concurrent 429 inside a window keeps the window, or shortens it when it states an earlier reset. The account's probe answers the account's window, not a model's own window: that model keeps its own probe time and gets its own probe. Under the account's bounded window, a model's own cooldown of any cause keeps its own deadline in that model's record, and the account's record holds the model until the account's probe, so an earlier account reset never brings the model back sooner; Go writes the later of the two deadlines into the model's record. The doubling count is separate from Go's `backoff_level` (which keeps its meaning) and is saved as an extra `quota.trust_windows` field on every quota record cliproxy-rs writes to `.cds` files, which Go ignores; records are saved only while their cooldown is running, so a restart after a window ended starts again at one hour. cliproxy-rs's own records restore as they were saved. `.cds` records written by Go or before this change get the first bound. A model's count is never lowered by a credential-wide window. The stated reset is kept: `.cds` records and error events report it as `quota.next_recover_at` (Go's meaning) and the probe time as `next_retry_after`, and the Management API's cooldown entries gain `recover_at`, so the dashboard shows "Limited until X · next check in Y"; such an entry stays listed, with `remaining_seconds` 0, after the window ends while the stated reset is ahead. The cost is one comparison per 429; a probe check on two keys per recorded result, per pick and per stream start; one scan of the cooldown entries when a stream start or a success ends an account's window; four bytes per cooldown entry and per request for the window generation; and per credential and model one real upstream request per window. `max-trusted-cooldown: 0` restores Go's behaviour. Set by a config reload, it applies to requests picked after the reload. A bounded window keeps its bound and ends with its probe, unless a 429 from such a request arrives inside it with a later stated reset, which then replaces the bound as in Go. Go starts with the key in `config.yaml` and ignores it; when Go's Management API rewrites the file, it moves the key into a comment, as it does with every key it does not know.
- Startup: if the config fails to load outside cloud deploy mode, cliproxy-rs exits with a non-zero status, so a service manager sees the failure. Go exits 0.
- Discovery: subtype PTR queries are answered (Go's zeroconf library never matches them) and answers go out on every selected interface.
- `.env`: non-UTF-8 bytes inside quoted values are decoded lossily. Go keeps the raw bytes.
- OAuth sign-in from the Management API: pending callbacks are held in memory with the sign-in session instead of being written to `auth-dir` as `.oauth-<provider>-<state>.oauth` files.
- Claude: `platform_url` is HTML-escaped on the sign-in result page, credential files are written atomically with mode 0600, and the SSH port-forwarding hint shows the IP address of the outbound interface.
- Plugins: loading plugins on Windows is not supported, the same as a Go build without cgo.
- Plugins, size limits where Go reads without one: a plugin frontend auth provider reads a request body of at most 64 MiB, the same limit as the routes, and a larger one is refused with `413` and `{"error":"request body too large"}` even when no key was sent. Plugin store responses (the registry, release metadata, release assets and direct artifacts) stop at 256 MiB, and a declared artifact size can only lower that. A library inside a plugin archive may expand to at most 256 MiB. `host.http.do` buffers at most 64 MiB of a response and then fails as a read error; `host.http.do_stream` is not limited. A quota probe's answer is read up to 64 MiB, like `requests/api-call`.
- Plugin store: a GitHub `X-Ratelimit-Reset` later than the end of year 9999 is treated as that time, so the cooldown stays printable. Go keeps any value.
- Discover mode: before plugins load, a flag that cliproxy-rs does not define (it may be a boolean flag a plugin adds) does not take a following `-discover` or `-discover-json` as its value, so `-some-plugin-flag -discover` runs discovery without loading plugins or `.env`. Go treats every flag it does not know as taking a value, then loads plugins and `.env` before the full parse selects discovery. Flags cliproxy-rs defines behave as in Go.
- Plugins, `.env`: the file is read before the plugins that add command-line flags load, so they see its variables. Go reads it after the flag parse.
- Plugin sign-in: when a sign-in returns several auth files and a later one fails to save, the earlier ones are undone without losing data. A file the sign-in created is removed, locally and from the configured store; a file that existed before gets its earlier contents back, and the store copy is synced from it. Go deletes both kinds, together with their store copies.
- Plugins, frontend auth: the metadata a plugin returns with an accepted request is not kept. In Go only Home mode reads it.
- Plugins, model routers: the available providers sent to a router list Kimi credentials typed `kimi.com` or `kimi.ai` under those keys, because credential selection here matches the key as written. Go lists them as `kimi` and `kimi-ai` and folds both spellings when it selects.
- Plugins, `host.http.*`: a URL whose host Go's parser and the WHATWG parser read differently is refused instead of being sent.
- Logs: structured fields that Go does not define are printed after Go's known fields.
- Process logs: the opt-in `--log-file PATH` flag replaces stdout through the existing 10 MiB rotating logger. With a positive `logs-max-total-size-mb`, its rotations share that budget with the normal log directory, even when PATH is elsewhere; the existing cleaner removes oldest logs on its minute schedule. With the default `0`, normal logs remain unlimited, but PATH's timestamped rotations have a separate 32 MiB total cap, enforced at startup, reconfiguration and rotation without another timer. Neither cleanup path deletes the file open for writing; that active file can exceed the budget. Outside the normal log directory, only PATH and its timestamped rotations are counted. `logging-to-file: true` still selects `main.log`, the dashboard log view and the existing size cleaner; turning it off returns to `--log-file`. Only the plain Windows server detaches its console, just before serving; login, import, discovery, TUI and plugin commands keep it. One output file is open when enabled, with no added thread, timer or work on inference requests beyond existing log writes. Go has no such flag.
- Working directory: the opt-in `--working-dir DIR` flag changes directory before `.env`, plugin bootstrap, config or relative paths are read. Windows installer launches pass it at sign-in as well as after installation. It has startup-only cost and is not passed in Go's plugin command-line values. Go has no such flag.
- Release checks: the dashboard checks only when clicked. `GET /server/latest-version` fixes the previously empty release URL using one anonymous HEAD to the public cliproxy-rs latest-release redirect, without following it. A successful tag is cached for 12 h (one timestamp and tag, no expiry timer). `CLIPROXY_NO_UPDATE_CHECK=1` disables checks at startup. Release checks use the configured `proxy-url`, or the environment proxy when none is set, and never send tokens or cookies; proxy credentials go only to your proxy, with TLS verification on and redirects off. Go asks its GitHub API on every call and can attach environment tokens; omitting those tokens is a credential-leak fix. Inference requests incur no added work.
- Config writes: when the Management API changes one setting, the rest of `config.yaml` stays byte for byte as it was. Go re-encodes the file, which turns YAML 1.1 booleans such as `yes` and `on` into `true`.
- Watcher: when a config change moves `auth-dir`, cliproxy-rs starts watching the new directory. Go keeps watching the old one until it restarts.
- Watcher, where file change notifications cannot be set up (inotify instance or watch limits on Linux, the descriptor limit on macOS, or an operating system other than Linux, macOS and Windows): cliproxy-rs logs one warning and checks the config file and auth files every 2 seconds instead. Go stops at start: with `cliproxy: failed to create watcher` when the inotify or kqueue instance cannot be created (or the OS has no fsnotify backend), and with `cliproxy: failed to start watcher` when the config file or auth directory cannot be added. On FreeBSD, OpenBSD, NetBSD, DragonFly and illumos/Solaris, Go reloads from kqueue or FEN events, while cliproxy-rs polls every 2 seconds. As in Go, changes made by another machine on a network or FUSE file system can go unreported until the next local change: on NFS, 9p (such as WSL2's /mnt/c) and sshfs they are not reported, and on SMB/CIFS shares they may not be, depending on the server (on Windows, ReadDirectoryChangesW asks the server for change notifications, which SMB 3.0 servers can send).
- Watcher, symlinks: cliproxy-rs also watches the folders that hold symlinks on the way to the config file, the auth folder and symlinked auth files, so a Kubernetes Secret update (the `..data` swap) or an `ln -sfn` to a new release folder is reloaded. Go's fsnotify watches only the config file and the auth folder and misses those.
- Token refresh: the refresh loop sleeps until the next token is due and looks again at least every 10 minutes of awake time while any credential can come due. Go looks every 30 seconds. After a computer wakes from sleep or the clock jumps forward, a token that expired in the meantime is refreshed by the first request that gets a 401 (one extra round trip; the other credentials are refreshed about a second later) or within 10 minutes.
- Model catalogs: outside Home mode, the Codex client catalog is first downloaded when a Codex credential exists, a Codex client asks for `/v1/models?client_version=...`, or a Codex client sends a Responses request with `client.codex.optimize-multi-agent-v2` on; the Devin catalog when a Devin credential exists. Go downloads both at start and every three hours whether or not they are used; in Home mode cliproxy-rs starts both at launch, as Go does. Until that first download finishes, Codex client catalog answers and the `spawn_agent` model lists use the catalog built into the binary; after it, they match Go. Every catalog refresh sends the `ETag` of the catalog it installed last as `If-None-Match`, so an unchanged catalog costs a `304`; Go downloads the whole file each time.
- Watcher startup: cliproxy-rs reads `config.yaml` once when the watcher starts, so an edit made after the config was loaded but before watching began takes effect. Go starts watching without rereading the file and keeps the older config until the next edit.
- Management panel: cliproxy-rs never downloads or updates its dashboard; it is built into the binary. Go downloads its panel from `management.panel-github-repository` when it is first requested and checks for a new one every three hours unless `management.disable-auto-update-panel` is set. cliproxy-rs accepts both settings, checks their types and keeps them in `config.yaml` (setting `panel-github-repository` to null through the Management API stores Go's default repository, as Go does), but nothing reads them. `management.disable-control-panel` still turns the built-in dashboard off.
- Sign-in errors: when a Codex, Kimi, Meta, xAI or Devin sign-in started from the Management API fails, the session error keeps Go's message, status and OAuth error code but leaves out upstream response bodies, OAuth error descriptions and decoder details. Go copies those in, and they can contain tokens, while the callback route shows session errors to anyone who holds the session state without a management key. For example, a failed Codex code exchange ends at "token exchange failed with status 400" where Go appends the response body.
- Masked keys in logs: Go masks API keys, tokens and secrets in request logs and query strings by keeping a few bytes at each end, but leaves a value of one or two bytes unchanged. cliproxy-rs writes `...` for those, so a short client key never appears in a log.
- AI Studio relay credentials in the Management API: a browser connected to `/v1/ws` is listed as a runtime-only credential. Its `created_at` is the time the Management API first listed it, and `updated_at` and `modtime` are the time it first listed the current version of the credential, so a status or fields edit moves them and a request does not. Go sets both when the browser connects and moves `updated_at` after every request result. The cliproxy-rs credential store keeps no timestamps.
- Deleting an AI Studio relay credential through `DELETE /v8/management/credentials` (or the v0 `auth-files`) answers 404 "auth file not found" and touches nothing on disk. The credential has no file, so Go falls back to `auth-dir/<ID>`: if a file of that name exists, Go deletes it and removes the credential as well.
- Cookies in request logs: Go writes `Cookie` and `Set-Cookie` values to request logs and forced error logs unchanged. cliproxy-rs writes `<redacted>` for the whole value of any header whose name contains `cookie`, in the client and upstream sections alike, because a session cookie is a credential. The headers sent upstream and back to the client are unchanged.
- Upstream URLs in request logs: Go writes the upstream URL of each captured request as it is, so credentials in a configured `base-url` reach the log. cliproxy-rs writes `<redacted>` in place of any `user:password@` part and masks sensitive query values (`key`, and names containing `api-key`, `apikey`, `api_key`, `token` or `secret`) the same way it masks the client URL. Requests still go to the URL as configured.
- Usage records for a canceled xAI request: when the client goes away while an xAI HTTP request is in flight, the failure record says `context canceled` with status 499, as in Go, but leaves out the method and URL that Go's text adds when the cancellation hit the send (`Post "<url>": context canceled`). A configured base URL can carry credentials in its query.
- xAI request logs: the API REQUEST section of an xAI video status poll says `HTTP Method: GET`, the method sent upstream. Go logs every xAI request as `POST`, including that `GET`.
- OAuth callback: the unauthenticated `POST /v8/management/oauth/callback` (and the v0 `oauth-callback`) accepts a body of at most 64 KiB. Go reads it without a limit. Real callbacks are a few hundred bytes; the limit protects servers reachable from the internet.
- Responses WebSocket: when a continuation pinned to its credential fails with 401 or 429, the client is always closed with 1012 (replay over HTTP). In Go, the same error also closes the upstream socket, and the disconnect watcher can close the client first with the error instead of 1012.
- Session affinity: a request without a session ID whose body nests more than 128 arrays and objects is not matched against earlier conversations by its messages; it keeps the session identity derived from its instructions and first user message, as a request without a client key does. Go matches it at any depth on its growable stacks, while the same walk on a native stack overflows and stops the server. Real conversations nest far less.
- Session affinity: when a routing change (strategy or a `session-affinity` setting) replaces the conversation matcher, its access counter keeps counting. In Go the new matcher starts again from zero, so a request picked before the change that fails afterwards can remove a conversation bound after the change, which loses that account until the next request binds it again.
- Request logs: when a logged body has a malformed Brotli encoding, cliproxy-rs can leave out the partly decoded bytes that Go writes to the log, and the decoder's error text differs from Go's. Well-formed compressed bodies are logged as in Go.
- Kimi, Meta and Devin request logs: when an upstream request fails before any response arrives, the `Error:` line of the API RESPONSE section has cliproxy-rs's own message, such as `upstream request failed`, where Go writes its HTTP client's error (`Post "<url>": ...`). An error response from Kimi or Meta is logged up to its first 16 MiB, the part cliproxy-rs reads; Go logs the whole body. When a Kimi or Meta stream ends with a read error and also fails the apply_patch end check, the log keeps the read error, which Go leaves out in that case.
- Devin request logs: the end-of-stream summary (thinking, content and signature) is collected only when `request-log` is on as the stream starts, so a stream nobody logs is not kept in memory. A stream that is already running when `request-log` is turned on gets no summary; Go collects one for every stream.
- Codex live request logs: in the logs of `POST /v1/live`, `POST /v1/realtime` and `POST /v1/realtime/calls`, the ICE credentials of SDP bodies (`a=ice-ufrag:` and `a=ice-pwd:` values, also inside JSON or multipart bodies) are written as `[REDACTED]`, in the downstream and upstream sections alike. Go logs those bodies unchanged. The bytes sent to the client and the upstream are not changed.
- `PUT /v0/management/config.yaml`: comment lines are unindented before the upload is checked, so the check sees the bytes that are written. Go checks the upload as sent and unindents while writing; when a `#` line sits inside a block scalar, Go can overwrite `config.yaml` with YAML that no longer loads and then answer `500 reload_failed`. cliproxy-rs answers `400 invalid_yaml` and leaves the file alone. Two answers differ from Go: a type mismatch such as `port: abc` is `422 invalid_config` (Go: `400 invalid_yaml`), and YAML syntax messages come from a different parser, so only the status and the error code match.
- Terminal UI (`-tui`):
  - Each reply goes to the tab that asked for it. Go hands replies to the active tab only, so a reply that arrives after a tab switch is lost (and an OAuth poll in progress never finishes).
  - While a text field has focus, every key except Ctrl+C goes to the field. Go still quits on `q`, switches language on `L` and changes tab on Tab while you type. On the password screen `q` and `L` keep their meaning while the field is empty.
  - The status bar sits on the last terminal row; Go leaves two empty rows under it.
  - Long lines are cut at the terminal edge: there is no horizontal scrolling (`h`/`l`). The cursor does not blink, and Ctrl+V does not read the system clipboard (a terminal paste works).
  - Adding a client API key sends `{"old": key, "new": key}`, which adds the key when it is missing. Go sends `{"old": null, "new": key}`, which its own server rejects with `400 missing fields`.
  - A delete or edit started on the Auth Files or API Keys tab acts on the item that was selected. Go resolves the list position again when you confirm, so a refresh in between can delete another file or change another key. API keys are addressed by position, so if a refresh moves the selected key the action is cancelled.
  - On a cliproxy-rs server, the OAuth tab marks Antigravity as not supported and does not start it. Go servers still offer it.
  - `-tui -management-base-url URL` is a pure client: it starts without a local config, store or Home bootstrap. Go loads them first, so it fails without a local config and waits in cloud mode.
  - `-tui -standalone` works without a management key in the config or `MANAGEMENT_PASSWORD`: its generated (or `-password`) password is accepted from loopback, also after a config reload. Go refuses every management request without a configured key, so its standalone TUI never connects then. The TUI connects to the address the server actually bound, so `port: 0` and IPv6 loopback work. A `server.tls` setup or a host that is neither loopback nor a wildcard address is refused with an error; in Go these fail after 30 connection attempts.
- `pprof` (planned; not in cliproxy-rs yet): the listener will serve the index, `cmdline` and `symbol`, and the CPU `profile` in builds with its optional feature. Profiles of the Go runtime (`heap`, `allocs`, `goroutine`, `block`, `mutex`, `threadcreate`, `trace`) have no Rust equivalent and will answer `501` with a plain message; without the feature, `profile` will answer `501` too and name the feature.
- WebRTC media relay for Codex live calls (`oauth.providers.codex.live-media-relay`): every Go build includes it, and the config turns it on. In cliproxy-rs it is an optional build feature (`cargo build --release -p cliproxy --features cpa-server/media-relay`); the release binaries and the Docker image are built without it, so calls negotiate media directly with the upstream. In a build with the relay, TURN servers reached over TCP or TLS are skipped with a warning, because the WebRTC library cannot gather candidates through them; TURN over UDP and STUN work. Candidate gathering for the upstream peer stops after 6 seconds and the call goes on with the candidates gathered so far, because the library never finishes gathering when a STUN server stays silent. Go waits until gathering completes or the request is cancelled, so a TURN server that takes longer than 6 seconds to allocate a relay address still contributes a relay candidate in Go but not in cliproxy-rs.
